论文：Stellex

NeoForge 21.1.x 生态下的可调 CPU 调度核心与客户端渲染剔除：设计、兼容性边界与实证测量。约 1.5 万汉字。

作者：Mornfrost Office

Stellex：NeoForge 21.1.x 生态下的可调 CPU 调度核心与客户端渲染剔除：设计、兼容性边界与实证测量

作者：Mornfrost Office

摘要

Minecraft 模组生态长期面对一对相互拉扯的目标：一方面，玩家与整合包作者希望服务端能把空闲算力用于地形预生成、区块预热等真实工作；另一方面，任何对加载器内核的改动都会破坏第三方模组赖以运行的二进制契约。本文以 NeoForge 21.1.x 为对象，讨论一种折中形态的工程可行性：不替换加载器与游戏内核，而把新增能力收敛为一个核心模组 Stellex。该模组在服务端实现一个以 JVM 系统属性配置目标占用比例的 CPU 调度器，通过区块票据驱动原版异步生成管线，在不空转、不制造无用计算的前提下填充空闲算力；在客户端实现两路基于距离的渲染剔除，分别作用于实体与方块实体渲染调用点。为论证该形态的必要性，本文系统梳理了自建内核与"完全兼容"之间的互斥关系，从 Mixin 目标偏移、访问转换器、Sinytra Connector 的转译依赖、运行时映射、事件时序与维护成本六个维度给出分析。实证部分报告了三组服务端调度实验、构建与启动耗时、产物规模以及 21.1.250 到 21.1.251 的版本迁移过程。实验显示：调度器可以在几乎不影响 tick 的前提下稳定驱动区块预生成（观测区间内 tick 中位数低于 8 毫秒，最坏 41.6 毫秒且仍维持在 20 TPS），但进程 CPU 占用并不会无限逼近目标比例，其上限由原版区块生成执行器的并行度决定，观测到的稳定区间约为 34% 到 62%。本文的结论是：在模组生态中，新增能力的正确落点是"带边界的行为扩展"，而非"内核重写"；同时，目标占用比例应被表述为闭环上限而非硬性承诺。

关键词：NeoForge；Minecraft 模组；CPU 调度；区块预生成；Mixin；兼容性；渲染剔除

1 引言

1.1 研究背景

Minecraft 的模组生态在 1.21.1 这一代形成了两套并行的加载器体系：Fabric 以轻量、快速跟进版本著称，NeoForge 则继承 Forge 传统，提供更完整的官方 API、事件总线与访问转换能力。二者之间的桥接由 Sinytra Connector 承担，它把 Fabric 模组的字节码映射到 NeoForge 与 Minecraft 的官方命名，并补齐 Fabric API 的运行时语义。对于一个希望"同时兼容两边"的新平台而言，这意味着它必须同时满足两套互不相同的契约。

服务端性能是模组生态中讨论最久的问题之一。玩家在探索新区域时会遇到区块生成造成的卡顿，服主则常常希望把服务器空闲的 CPU 核心利用起来，提前把地形生成好。围绕这一需求，社区已经出现了 Chunky 一类预生成工具，它们的工作方式是主动遍历区块并阻塞等待生成结果。这类工具有效，但缺少对进程整体 CPU 占用比例的控制，也缺少与 tick 预算的显式联动，容易在配置不当的情况下把服务器拖入低 TPS 状态。

客户端性能则是另一个长期痛点。大型整合包中实体、方块实体、粒子与模型数量急剧上升，帧率下降通常被笼统归因于"模组太多"。工程上更准确的说法是：渲染管线中仍存在大量"当前不可见却仍然付出代价"的对象，例如视野外但仍在渲染距离内的方块实体、被地形遮挡的实体等。对这些对象做剔除，是风险较低、收益可度量的一类优化。

1.2 问题定义

这一工作的目标可以拆解为六条硬性约束：其一，以 NeoForge 1.21.1（21.1.251）为基础；其二，照搬 NeoForge 的其余部分；其三，完全兼容 NeoForge 模组；其四，完全兼容经 Connector 转译的 Fabric 模组；其五，新增一个能把服务器 CPU 按 JVM 参数可调比例"榨干"的大功能，且不得空转白占；其六，必须可编译，且 Stellex 客户端、Stellex 服务端与普通 NeoForge 客户端、普通 NeoForge 服务端之间要能双向进入，客户端还要缓解模组过多导致的帧率过低。

这六条约束在形式上并不矛盾，但在实现路径上存在一个关键分叉：如果把"照搬 NeoForge 源码"理解为"复制源码、改名、另建内核"，那么第三、四条会立刻失效；如果把"照搬"理解为"保留 NeoForge 内核、在其上扩展"，那么全部约束可以同时满足。本文的核心工作之一，就是把这个分叉论证清楚，并给出后一种路径的完整实现与测量。

1.3 主要贡献

本文的贡献可以归纳为四点。第一，给出自建内核与完全兼容互斥的六维分析，指出兼容性的定义权掌握在第三方字节码而非平台声明手中。第二，设计并实现了一个票据驱动的服务端 CPU 调度器，它把目标占用比例作为闭环上限，用 tick 预算与 CPU 采样双重反馈约束投喂速度，并在队列排空时完全停机。第三，设计并实现了两路客户端渲染剔除，给出注入点选择、包围盒判定、Boss 类豁免与注入失败降级的具体方案。第四，报告了覆盖构建、启动、运行三个阶段的一手测量数据，并诚实标注了单一硬件、单一版本、缺少图形环境验证等效度威胁。

2 相关工作

2.1 加载器与兼容层

Fabric 的 Mixin 生态以运行时映射与轻量注入为核心，模组通过 fabric.mod.json 声明依赖，通过 Mixin 配置在类加载期改写字节码。NeoForge 则在 Forge 的基础上重构了事件系统与模组发现流程，运行时使用 Mojang 官方命名，因此 Mixin 配置通常不需要 refmap。Sinytra Connector 位于两者之间，它必须在 NeoForge 的类加载与事件时序之上重建 Fabric API 的语义，包括但不限于注册表、网络通道、生命周期事件与 Mixin 兼容层。

从工程角度看，Connector 的存在提高了"内核可替换性"的门槛：任何试图替换 NeoForge 内核的方案，都必须同时复刻 Connector 所依赖的内部结构，而 Connector 的实现细节会随版本变化。这一点在本文第 3 节会被展开为具体机制。

2.2 服务端性能工作

服务端侧的公开工作大致分为三类：预生成工具（如 Chunky）、区块加载优化（调整票据与加载距离）、以及 tick 级性能分析（如 Spark）。预生成工具的典型实现是在服务端主线程上按区块坐标循环调用 getChunk，依赖原版异步生成管线完成实际计算，主线程只承担调度与等待。这类实现简单可靠，但对"占多少 CPU"没有显式控制。

本文的调度器与上述工作共享同一底层机制（区块票据与原版生成管线），差异在于控制层：把"是否投喂新任务"与"进程 CPU 采样"和"当前 tick 是否有空闲预算"绑定，并把目标比例作为反馈目标而不是硬编码的吞吐参数。

2.3 客户端渲染优化

客户端优化模组已经形成了较完整的谱系：Sodium 及其分支重写了区块渲染与部分实体渲染路径；EntityCulling 通过遮挡查询与视锥测试剔除不可见实体；Lithium 优化游戏逻辑与 AI；FerriteCore 降低内存占用；ModernFix 处理启动与资源加载。这些模组各自覆盖不同的优化面，彼此之间既有协同也有冲突。

Stellex 的客户端部分刻意选择了最小侵入的定位：不重写渲染管线，只在两个既有调用点上增加距离判定。这使它的收益上限低于 Sodium 一类的重写型方案，但兼容面更宽，且行为可以逐项关闭、逐项观测。第 6 节会说明这一取舍的具体依据。

2.4 研究缺口与本文定位

已有工作大致落在两个极端：一端是重写型优化（Sodium、Lithium 一类），收益显著但需要深度介入渲染与逻辑管线，兼容成本高；另一端是独立工具型方案（Chunky 一类），介入浅但缺少与 tick 预算、进程 CPU 目标的联动。两端之间缺少的是"以最小介入获得可控收益"的中间形态：既不重写管线，也不做与主线程争抢的阻塞式循环，而是把新增行为挂在公开事件与公开 API 上，并用反馈控制约束其强度。

本文把 Stellex 定位在这一中间形态，并把它放在兼容性约束下检验。与研究加载器内部机制的文献不同，本文关心的不是"如何改得更深"，而是"在不改的前提下还能做到什么，以及这样做的代价是什么"。这一提问方式使得兼容性不再是事后检查项，而是设计输入：每增加一个注入点或一次 API 调用，都要回答它是否落在第三方字节码依赖的目标集合之外。

3 形态选择：为什么不是内核 fork

3.1 兼容性的定义权

一个模组能否在某个平台上运行，并不由平台自己的声明决定，而由第三方字节码里写死的东西决定：Mixin 配置中的类名、方法名与描述符，访问转换器引用的成员，Fabric 模组在 Connector 下的映射目标，FML 的事件时序，以及 mods.toml 中的加载器依赖。这些目标集合构成了事实上的应用二进制接口（ABI）。由此可以给出一个简洁的互斥论证：完全兼容意味着第三方字节码依赖的全部目标在运行时仍然存在且语义不变；另写内核意味着这些目标中至少有一类会被替换、移动或重新映射；二者不能同时为真。若要让重写后的内核也满足完全兼容，就必须让类名、包名、方法描述符、访问转换结果与事件时序逐项与 NeoForge 一致，而做到这一点在工程上等价于没有重写。因此现实的选择只有两种：保留 NeoForge 并追加行为，或者接受兼容性下降，不存在稳定的中间态。

这一论证不是抽象推演。在 NeoForge 21.1.251 的 userdev 产物中，补丁文件数量为 957，patched 源码树的 Java 文件数量为 6317，源码中带有 // Neo: 标记的补丁点共 323 处，访问转换器规则文件 545 行，universal 产物内的条目数为 2521。这些数字共同描述了一个高度定制化的运行时，任何"照搬后改名"的做法都必须逐项复刻它们，且要在每个 Minecraft 补丁版本上重放。

3.2 六类具体机制

Mixin 目标偏移。 补丁会改变方法体、局部变量索引与调用序列。以 LevelRenderer#renderLevel 为例，NeoForge 的补丁在该方法及其调用的渲染阶段中插入了渲染阶段分发、方块实体可见性判断与自定义描边等逻辑。在反编译参考树中，BlockEntityRenderDispatcher#render 的两个调用点位于 LevelRenderer 的第 1075 行与第 1090 行，而 NeoForge 的 ClientHooks.isBlockEntityRendererVisible 守卫分别位于第 1052 行与第 1083 行。模组的 @Redirect 若以调用点计数或序号定位，一旦内核增删调用点，注入就会失败或漂移到错误位置。

访问转换器管道。 NeoForge 的 accesstransformer.cfg 共 545 行规则，把原本不可见的成员开放给模组。模组直接编译到这些被开放后的成员上；自建内核若少复刻任何一条，依赖它的模组会在运行时抛出 NoSuchMethodError 或 IllegalAccessError，若复刻了但作用对象不同，则表现为更隐蔽的行为差异。访问转换还决定了 Mixin 能访问哪些成员，等于改变了整个可注入面。

Connector 的内部依赖。 Sinytra Connector 不是独立运行时，它运行在 NeoForge 之上，依赖 FML 的事件时序、模组元数据与运行时映射，并在这一基础上重建 Fabric API。它对 NeoForge 内部的假设一旦被改写，失效的不是个别功能，而是整条转译链路。Stellex 之所以能与 Connector 共存，直接原因是它只使用公开 API 与公开事件，没有出现在 Connector 需要重映射或绕开的任何一条路径上。

运行时映射。 NeoForge 21.x 运行时使用 Mojang 官方命名，Mixin 配置因此可以不带 refmap，注入直接按描述符匹配。Stellex 的两个客户端 Mixin 都没有 refmap，等于把自己绑定在"运行时名等于官方名"这一契约上。自建内核若引入自己的映射层，所有不带 refmap 的 Mixin 会整体失配；若保留官方名，则又与"重写内核"的动机矛盾。

元数据与事件时序。 NeoForge 在 MinecraftServer 的补丁中定义了 tick 边界与生命周期事件的触发位置，模组在这些时间点上做初始化、IO 与状态同步。自建内核一旦移动 tick 边界或事件触发点，依赖时序的模组行为会漂移且极难归因。Stellex 的做法是只订阅、不拦截：入口类只注册了服务端启动、停止、tick 前后与命令注册五类监听器。

维护成本。 957 个补丁、6317 个源文件、545 行访问转换规则，是每次 Minecraft 与 NeoForge 升级都要重放的工作量。Connector 与优化模组会持续跟随 NeoForge 内部实现，自建内核永远落后一个版本。使用者在这种"要兼容就用官方内核、要 Stellex 就不能用某个模组"的二选一中，实际会放弃自建内核。

3.3 形态结论

综合上述六点，本文把 Stellex 定义为 NeoForge 21.1.x 上的核心模组：一个普通 mods/ 目录下的 jar，依赖 neoforge，通过 @Mod 构造注入与事件总线接入，不注册自定义网络通道，客户端 Mixin 只登记在 client 数组。这一形态同时满足双向进入、模组兼容、可选安装与新增功能四项要求，代价是能力边界清晰：不能修改 Minecraft 内部语义，服务端只能通过公开区块 API 与事件调度，客户端只能改渲染调用点。这恰好覆盖了研究目标所需的范围。

3.4 发行版的正确做法

如果确实需要以"Stellex 服务端""Stellex 客户端"的名义分发，正确做法是分发组合而不是分发新内核。具体而言：基座使用 NeoForge 官方安装器产出的服务端与客户端；mods/ 中放置 Stellex 与自行选择的模组；服务端通过 user_jvm_args 注入调度器参数；客户端通过配置文件模板给出两套预设（保守与激进）；分发渠道使用实例包或整合包格式，并在清单中只列经过验证的可选模组。

需要明确禁止的做法包括：替换 NeoForge 内核、修改 NeoForge 版本号、打包改过的 Minecraft 类、预置访问转换规则、覆盖加载器配置、在未获许可时内置他人的模组 jar。这些做法中的任何一条都会把"组合分发"退化为"内核替换"，从而回到第 3.1 节论证的互斥困境。发行前的检查清单应当覆盖四种安装组合各一次冒烟、一个 Connector 环境的 Fabric 模组冒烟、与 Sodium 及 EntityCulling 各一次客户端进入世界测试，以及 21.1.x 版本矩阵上的构建验证。

4 系统设计

4.1 总体结构与模块划分

工程为单 Gradle 子项目，源码按职责分为三块。入口包 com.mornfire.stellex 只包含 StellexCore，负责把 NeoForge 事件接到具体模块，不含业务逻辑。服务端包 com.mornfire.stellex.governor 包含调度器设置、CPU 采样、区块计划器、调度器主体与命令实现。客户端包 com.mornfire.stellex.client 与注入包 com.mornfire.stellex.mixin.client 只在物理客户端加载。资源侧仅有模组元数据、Mixin 配置与语言文件，没有网络通道注册，没有自定义负载类型。

全部 Java 源码为 11 个文件、1415 行，打包后的模组 jar 为 29742 字节、22 个条目。这一规模是刻意控制的：新增能力越少，与其他模组发生字节码层面交互的面就越小，兼容性论证也越容易成立。

4.2 事件接线

入口类在构造阶段注册五类监听器：服务端启动时创建调度器，服务端停止时释放票据并关闭，tick 前记录起点，tick 后执行采样与投喂，命令注册时挂载 /stellex 子命令。所有监听器都挂在 NeoForge 的游戏事件总线上，不替换任何加载器行为。客户端侧采用自注册方式：StellexClientInit 通过 @EventBusSubscriber(modid = "stellex", value = Dist.CLIENT) 只在客户端注册，监听 ClientTickEvent.Post，首个 tick 惰性加载配置并推进统计。这样入口类不需要引用任何客户端类型，从结构上避免了专用服务端加载客户端类的问题。

4.3 元数据与兼容声明

模组元数据声明依赖 neoforge [21.1,21.2) 与 minecraft [1.21.1,1.21.2)，两侧都限制在 1.21.1 系列内。这一范围是审计后的修正：早期写法 [21.1,) 会允许加载器在 21.2 及以后版本上加载本模组，而 21.2 对应 Minecraft 1.21.2，渲染与区块 API 存在变化，属于未验证区域。Mixin 配置把 injectors.defaultRequire 设为 0，含义是注入点匹配失败时记录警告并跳过，而不是让客户端崩溃。这一取舍偏向"广泛兼容"：代价是某一路剔除可能静默失效，因此统计日志与警告必须一起观察。

4.4 不注册通道的设计约束

双向进入的关键在于协议层没有 Stellex 的必装项。实现上，Stellex 不注册任何 CustomPacketPayload，不监听 RegisterPayloadHandlersEvent，不发起任何自定义握手。服务端只把调度器状态通过命令反馈给具有权限的管理员；客户端只做本地渲染决策。于是四种安装组合都成立：普通 NeoForge 客户端可以进入 Stellex 服务端；Stellex 客户端可以进入普通 NeoForge 服务端；两端都装时功能完整；两端都不装时一切照常。

4.5 生命周期与线程安全

调度器的全部可变状态都由服务端主线程独占：在途集合、票据集合、计划器队列、tick 起点与采样时间戳都只在 tick 回调中读写。跨线程可见性只用于少数几个标量，例如目标百分比、暂停标志与最近的 CPU 采样值，它们以 volatile 语义发布，避免在热路径上加锁。启动顺序被刻意安排在 ServerStartedEvent 之后：此时世界、区块源与票据管理器都已就绪，登记票据不会落到未初始化的状态上。关闭顺序安排在 ServerStoppingEvent 中：先置运行标志为假，再释放全部在途票据，最后清空计划器队列，这样区块保存流程看到的是"没有额外票据"的状态，不会在退出阶段被未完成的生成任务拖住。

单机内置服务端默认不启用调度器。原因不是技术限制，而是产品取舍：单机玩家的帧率与内置服务端的 tick 共享同一台机器的算力，后台预生成会直接抬高客户端帧时间。需要时可以用 -Dstellex.cpu.integrated=true 显式开启，但这属于高级用法，文档中已标注风险。

幂等性方面，调度器用静态的活动实例指针保证同一进程内只存在一个实例；重复的启动事件不会创建第二个调度器，重复的停止事件也不会重复释放票据。命令面对状态的影响是即时的：/stellex target 修改目标百分比后，下一次采样就会按新目标调整在途上限；/stellex pause 只停止投喂，不打断已经在途的任务，避免出现"暂停即丢工作"的语义。

5 服务端 CPU 调度器

5.1 票据语义的精确推导

原版区块系统的加载状态由票据等级决定。DistanceManager 中 addRegionTicket(TicketType, ChunkPos, int distance, T value) 的实现是 new Ticket<>(type, ChunkLevel.byStatus(FullChunkStatus.FULL) - distance, value)，即票据等级等于 33 减去传入的距离。这一行代码决定了一个容易踩的坑：传入距离 33 得到的不是"等级 33"，而是等级 0，也就是实体刻级别，区块会被完整刻并承担实体与方块实体刻的开销；传入距离 0 才得到等级 33，即"已生成但不刻"的状态。

本文的第一版实现恰好踩了这个坑：以 33 作为距离登记票据，随后在客户端测试之外的服务端实测中观察到 CPU 被抬高、tick 一度逼近 56 毫秒，而生成计数长时间为 0。修正后以距离 0 登记票据，区块按"已生成、不刻"的语义加载，CPU 与 tick 立即回到预期区间。这个细节也说明：在模组语境下讨论"榨干 CPU"，第一步是把原版语义读准确，否则所谓优化会把服务器拖入更差的状态。

5.2 计划器

计划器只在服务端主线程运行。它以每个在线玩家所在区块为中心，按配置半径展开方形环，去重后按到最近中心的距离平方排序，输出由近及远的候选队列。队列会跳过三类坐标：已经加载的区块（通过 getChunkNow 判定）、已经登记且在途的区块、以及本轮会话内已经完成的区块。队列上限为 32768，刷新间隔为 40 tick，避免每 tick 重建候选集带来的额外开销。

计划器还支持一个可选的固定锚点：当配置了 -Dstellex.pregen.anchor=x,z 且没有玩家在线时，以该区块坐标为中心继续预生成，用于开服前铺设出生点；不配置锚点时，无人在线即完全停机。锚点机制同时为实验提供了可复现的测量条件——把预生成目标放在远离出生点的空白区域，可以排除玩家活动对结果的干扰。

在实现过程中，计划器还暴露了一个典型的时间差溢出缺陷：初始的"上次刷新 tick"被设为 Long.MIN_VALUE，导致 tick - lastRefreshTick 溢出为负数，刷新条件恒不满足，调度器因此长时间空转而不产出。把初值改为一个足够小的有限负数后，该问题消失。这个缺陷在单元层面很难发现，只有在真实服务端运行并用命令观测计数时才会暴露，这也是本文强调"运行期观测"而非仅静态检查的原因。

5.3 投喂与反馈闭环

调度器每 tick 在主线程执行一次投喂。触发条件依次为：调度器处于运行状态、未暂停、预生成开关打开、存在玩家或锚点、当前 tick 仍有空闲预算（ServerTickEvent.Post#hasTime()）、以及未触发 tick 保护。满足后按预算从计划器取坐标，登记票据并记录起始 tick。

允许同时在途的区块数量由闭环控制：初始值取自 pregen.inflight，随后每 500 毫秒采样一次本 JVM 进程的 CPU 使用率。若采样值高于目标 3 个百分点，按当前值的四分之一收缩；若低于目标 5 个百分点，则加 2，直到上限。若平均 tick 耗时超过保护线（默认 45 毫秒），在途上限减半并停止投喂新任务，直到 tick 回落到保护线以下。采样不可用的 JVM 上退化为固定上限，不因读不到指标而失控。

这种设计把"目标百分比"定义为闭环上限而非硬性限制：调度器会朝目标加码，但不会为了凑数字而制造计算，也不会在服务器本身繁忙时与之争抢。这也是"不白占"原则的实现方式——所有 CPU 消耗都对应一个真实的区块 future 或一次真实的区块生成。

5.4 完成检测与资源回收

第二版实现不再等待区块 future，而是采用"主线程轮询完成"的方式：每 tick 遍历在途集合，对每个坐标调用 getChunkNow；若返回非空，说明区块已经生成并处于已加载状态，此时释放票据、标记完成、累计生成计数与花费 tick 数；若超过 1200 tick（约 60 秒）仍未完成，则释放票据并计入失败。选择这一方式的原因是：跨线程等待 future 会在主线程产生额外的调度开销，且一旦 future 链路异常，工作线程可能长时间挂起；而轮询方式把全部状态变更收敛到主线程，失败路径与超时路径都显式可控。

已完成集合用于避免会话内重复排队，容量上限为 262144 条；超过后整体清空，代价仅是后续区块从磁盘读取而非重新生成。在途集合、票据集合与计划器队列在调度器关闭时统一释放，避免服务器停止后残留票据。

5.5 配置面与命令面

调度器的全部参数都可以通过 JVM 系统属性配置：stellex.cpu.enabled（总开关）、stellex.cpu.target（目标百分比，默认 50）、stellex.cpu.threads（并发提示，默认核心数减 2）、stellex.tps.guard.ms（tick 保护线，默认 45）、stellex.pregen.enabled、stellex.pregen.radius（默认 32）、stellex.pregen.inflight、stellex.pregen.anchor 与 stellex.cpu.integrated（是否在单人内置服务端启用，默认关闭）。运行期可以通过 /stellex status、target、radius、pause、resume、reset 调整，权限等级为 2。

/stellex status 输出一行结构化状态，包含运行/暂停/保护中标记、目标与实测 CPU、在途数量与上限、队列长度、生成与失败计数、平均每区块耗时、tick 均值与 TPS 估算、保护线与半径、锚点。这样一行输出同时承担了可观测性与可复现性两个作用：实验记录可以直接引用它，运维也可以据此判断当前状态。

5.6 异常路径与超时处理

调度器的异常处理遵循"宁可少做，不可做错"的原则。登记票据的调用被包在兜底捕获中，任何异常只会计入失败计数并中断本轮投喂，不会向外抛出；释放票据同理，即使票据已经不存在，也只记录调试日志。生成检测路径不依赖 future 的回调，因此不存在回调线程与主线程竞争的问题；唯一需要处理的异常情形是区块在途期间因其他原因被卸载，此时 getChunkNow 会持续返回空，直到超时路径介入。

超时阈值设为 1200 tick，约 60 秒。选择这一数值的依据是观测到的平均每区块耗时：在邻接准备阶段，单个区块的完成时间可以达到 40 秒量级，若阈值过短会误杀正常任务；而在稳定阶段，耗时通常低于 10 秒，60 秒足以覆盖绝大多数正常情况，同时避免异常任务长期占用票据。超时后的处理不是重试，而是释放票据并计入失败，让计划器在下一轮刷新时重新评估该坐标——如果该区块确实无法完成，反复重试只会放大问题。

内存边界同样被显式控制：在途集合的大小不会超过在途上限，计划器队列上限为 32768，已完成集合上限为 262144 并在越界时整体清空。按每个坐标键值约 40 到 60 字节的保守估计，三者的内存占用都在数 MB 量级以内，不会随运行时间无限增长。这一设计针对的是长期运行服务器的真实场景：如果记账集合只增不减，玩家持续探索数周后可能积累数十万条记录，形成难以归因的内存缓慢上涨。

6 客户端渲染剔除

6.1 注入点选择

客户端优化只有两处注入。实体一路注入 EntityRenderer#shouldRender 的方法头，签名擦除后为 (Entity, Frustum, double, double, double)Z。选择该方法的原因是它位于实体渲染的最前端：一旦判定不可见，后续的模型查找、骨骼变换与顶点提交都不会发生，收益是完整的渲染链路，而不仅仅是一次视锥测试。方块实体一路使用 @Redirect 替换 LevelRenderer#renderLevel 内的两处 BlockEntityRenderDispatcher#render 调用，分别对应可见区块段内的方块实体与全局方块实体列表。选择重定向而不是在 render 内部注入，是为了让被剔除的对象连渲染器查找都跳过。

6.2 判定规则

实体一路的判定顺序是：总开关、距离是否大于 0、noCulling 标志、是否为玩家、是否为本机玩家、是否发光、是否有自定义名称，最后比较实体坐标到相机的距离平方。默认距离为 128 格。末影龙与凋灵被显式豁免，因为它们的可见性具有玩法意义，超出距离后整只消失会造成明显的视觉与体验问题。

方块实体一路先用 BlockEntityRenderer#getRenderBoundingBox 取得渲染包围盒，取不到时退回方块本体的包围盒，再计算相机到包围盒的最近距离；默认距离为 96 格。使用渲染包围盒而非方块中心，是为了覆盖信标光柱、末地折跃门光柱以及大型模组多方块结构这类"渲染范围远大于方块本体"的对象。准星指向的方块实体永远不剔除，避免出现"看着它却消失"的异常感。

两路判定都不做内存分配，不读磁盘，不抛异常；方块实体一路的判定被包在运行期异常兜底中，任何意外都退化为原版渲染。这些约束是为了让注入点在渲染热路径上保持廉价且安全。

6.3 配置与降级

客户端配置位于 config/stellex-client.properties，包含总开关、两路距离与统计间隔四个键，默认值分别为 true、128、96、1200 tick。配置在第一个客户端 tick 惰性加载一次，缺失时写出带英文注释的默认文件，读取失败时保留默认值并记录警告。统计日志每 1200 tick 输出一行，包含窗口期与累计的实体、方块实体剔除数量。

Mixin 配置的 defaultRequire 为 0，是"降级而非崩溃"策略的具体落点。在与其他渲染模组共存时，若某个注入点被整体改写而找不到目标，Mixin 只记录警告并跳过该注入，客户端仍可进入世界；代价是该路剔除静默失效，需要通过日志中的警告与统计行判断。这一策略把"兼容性优先"从口号变成了可执行的配置。

6.4 已知冲突面

对第三方优化模组的字节码核对显示：Sodium 0.8.13 把方块实体渲染搬进了 SodiumWorldRenderer，并在 renderLevel 的全局方块实体字段处注入，原版的两处调用不在其执行路径上，因此 Stellex 的重定向能应用但运行期基本不生效，统计会长期为 0；实体路径与 Sodium 的视锥包装可以共存。EntityCulling 1.11.3 分别在 LevelRenderer#renderEntity 与 BlockEntityRenderDispatcher#render 的头部取消，职责与 Stellex 重叠但目标不冲突，会遮蔽 Stellex 的统计。Create 6.0.10 的部分渲染器以 shouldRenderOffScreen 进入全局方块实体列表且视图距离达到 192，在纯原版路径下位于 96 到 192 格之间时会被 Stellex 剔除，这是需要按需调整距离或关闭该路的具体场景。

6.5 配置时序与统计口径

配置加载发生在第一个客户端 tick，而不是模组构造阶段。这样安排的原因有两个：一是 FMLPaths.CONFIGDIR 在构造阶段虽然可用，但此时玩家尚未进入世界，提前读盘对启动时间只有负面影响；二是配置的生效对象是渲染热路径，只有在世界存在之后才有意义。代价是首个 tick 之前的极少数帧仍使用内置默认值，如果配置把距离设为 0（关闭），这几帧仍可能按默认值剔除。这一窗口在实测中通常只有数帧，影响可以忽略；若要彻底消除，可以把加载提前到客户端初始化事件中，但会引入额外的启动 IO，本文选择了前者。

统计口径需要区分窗口值与累计值。窗口值是自上次报告以来被剔除的对象数量，累计值是自客户端启动以来的总量；前者用于判断"当前场景下这一路是否真的在起作用"，后者用于观察总体趋势。日志只在世界非空时推进，因此停留在主菜单时不会产生噪声。统计间隔最小为 1 tick，负值与零会被修正，避免出现除零或每帧刷屏。

配置的容错策略是"保留默认、记录警告、不覆盖已有配置文件"。文件不存在时写出带注释的默认文件；文件存在但解析失败时保留默认值并记录警告，不重写文件，避免把手写配置冲掉。距离为负数时按 0 处理，等价于关闭该路；间隔小于 1 时按 1 处理。这些规则都是为了让"配置写错"退化为"优化不生效"，而不是"客户端无法启动"。

7 兼容性验证

7.1 静态核验

兼容性论证不能只停留在设计声明，本文对实现做了三类静态核验。第一类是通道核验：在全部源码中检索 RegisterPayloadHandlersEvent、CustomPacketPayload、PayloadRegistrar、SimpleChannel 与 PacketDistributor 等符号，结果为空；对 net.neoforged.fml 的引用仅限 ModContainer、@Mod、FMLPaths 与 @EventBusSubscriber 四个公开入口。第二类是注入点核验：对 21.1.250 与 21.1.251 的合并 jar 执行 javap，确认 EntityRenderer#shouldRender 的描述符为 (Lnet/minecraft/world/entity/Entity;Lnet/minecraft/client/renderer/culling/Frustum;DDD)Z，BlockEntityRenderDispatcher#render 的描述符为 (Lnet/minecraft/world/level/block/entity/BlockEntity;FLcom/mojang/blaze3d/vertex/PoseStack;Lnet/minecraft/client/renderer/MultiBufferSource;)V；对 LevelRenderer#renderLevel 的字节码检查确认两处调用点的偏移分别为 1586 与 1739，与重定向目标一致。第三类是版本对照：21.1.250 与 21.1.251 的补丁集合差异未改变上述两个描述符，说明注入点在该补丁区间内稳定。

7.2 版本迁移

实验环境无法直连 maven.neoforged.net：域名解析返回了包含 face:b00c 特征段的地址，443 端口不可达，属于典型的网络层干扰。为完成 21.1.251 的迁移，本文使用 BMCLAPI 的 maven 镜像代理拉取全套产物，并逐一核验。拉取结果如下：universal 包 3551265 字节，userdev 包 3983886 字节，sources 包 1796948 字节，installer 包 6972016 字节，moddev 配置 10239 字节，pom 7782 字节，Gradle 模块元数据 20592 字节，合计约 16.33 MB。版本真实性通过三处交叉确认：pom 中的 <version>21.1.251</version>、moddev 配置中的 net.neoforged:neoforge:21.1.251 引用、以及模块元数据中的 "version": "21.1.251"。

迁移过程中出现过一次可复现的构建失败：仅放置 pom 与 jar 而未放置 Gradle 模块元数据时，依赖解析报变体匹配失败，耗时 1 分 38 秒。补齐 .module 文件后，构建耗时 10 分 54 秒并成功，其中 NeoForge 补丁应用 17.81 秒、源码变换 55.01 秒、5364 个源文件重编译 171.63 秒。迁移完成后，专用服务端在 21.1.251 上启动成功，模组列表显示 NeoForge 21.1.251 (neoforge) 与 Stellex Core 1.0.0 (stellex)，调度器正常启动，/stellex status 可通过 RCON 查询。

7.3 行为验证的边界

必须区分"已验证"与"未验证"。已验证的部分包括：构建通过、专用服务端加载、调度器启动与命令响应、票据驱动的区块生成计数增长、tick 保护触发与恢复、客户端注入点在两个补丁版本上的描述符匹配。未验证的部分包括：客户端 Mixin 在真实图形环境中的运行效果与帧率收益、Sodium/Iris/Embeddium 等模组的实际共存、Connector 环境下的 Fabric 模组转译行为、纯原版客户端进入模组服务端时的具体交互。本文在讨论与限制部分会对这些边界逐项说明，不把它们混入已验证结论。

7.4 四种安装组合的验证矩阵

双向兼容需要在四种安装组合下分别成立，因此验证矩阵也应分成四格。第一格是普通 NeoForge 客户端进入 Stellex 服务端：服务端多加载了一个模组，但它不注册通道、不改变握手，客户端侧看到的模组列表变化只影响显示，不影响连接；验证方式是让未安装 Stellex 的客户端完成登录并进入世界。第二格是 Stellex 客户端进入普通 NeoForge 服务端：客户端的 Mixin 只在本地生效，服务端无需知晓；验证方式是让安装了 Stellex 的客户端连接原版服务端并观察日志中是否有注入警告。第三格是两端都装：这是功能完整形态，调度器与客户端剔除同时可用。第四格是两端都不装：作为基线，用于确认性能差异确实来自 Stellex 而不是环境变化。

在本文的实验环境中，第三格与"服务端单独安装"的场景已通过专用服务器与 RCON 间接验证；第一格与第二格需要真实图形客户端，受限于无图形环境未能实测，这是本文最主要的效度缺口。需要说明的是，这一缺口并不影响服务端侧结论，因为服务端行为不依赖客户端是否安装 Stellex；它影响的是"客户端剔除在真实渲染环境中的表现"这一部分。

8 实验与数据

8.1 实验环境与协议

实验在一台 Windows 10 机器上进行，JVM 为 Oracle HotSpot 21.0.8，可见物理内存约 8 GB，逻辑处理器数量为 4（由 stellex.cpu.threads 的默认值核心数减 2 得到 2 反推）。服务端为开发环境专用服务器，NeoForge 版本在 A、B 两组为 21.1.250，在 C 组为 21.1.251，Minecraft 1.21.1，世界种子 12345，视距 6，模拟距离 4。

测量协议如下：服务端启动完成后，通过 RCON 每 20 秒执行一次 /stellex status，连续采样三次，随后发送 stop 正常关闭。每组实验在空白区域设置不同的固定锚点，以排除玩家活动干扰并尽量避开已生成区块：A 组锚点 (2000,2000)，B 组 (4000,4000)，C 组 (6000,6000)。由于锚点不同，三组所处地形的复杂度并不完全一致，这是本文数据的主要混淆因素，后文在解释差异时会明确标注。CPU 指标来自 JVM 的进程级采样，统计口径是整个进程而非调度器自身；tick 指标为服务端最近若干 tick 的滑动平均。所有数值均为单次运行的观测值，未做多次重复取中位数，因此应被视为工程测量而非严格基准测试。

8.2 构建与启动数据

构建方面，21.1.250 的首次完整构建（含 NeoForm 反编译与重编译）耗时 11 分 37 秒；切换到 21.1.251 后的完整构建耗时 10 分 54 秒；在同一版本上的增量构建（仅改动数个源文件）耗时 12 到 15 秒。首次构建的耗时要明显高于后续构建，原因是 NeoForm 管线需要完成反编译、补丁应用、源码变换与 5364 个源文件的重编译，这些中间产物在后续构建中被缓存复用。

启动方面，三种世界状态下的 Done 耗时差异显著：全新世界首次启动为 194.474 秒，其中出生点准备阶段占 94.282 秒；已有世界重启为 89.306 秒；已充分生成且视距较小的世界为 11.933 秒。这说明服务端启动时间主要由世界生成状态与出生点准备决定，与 Stellex 的引入没有可观测的关联——调度器在服务端启动完成后才初始化，且默认不在内置服务端启用。

8.3 调度器实测数据

A 组条件为目标 80%、在途上限 4、半径 6、锚点 (2000,2000)、NeoForge 21.1.250。三次采样的原始数据为：

  • 第 1 次（约启动后 30 秒）：CPU 40.3%，在途 4/4，队列 151，已生成 14，平均每区块 10461 毫秒，tick 7.96 毫秒；
  • 第 2 次（约 50 秒）：CPU 51.6%，在途 1/4，队列 142，已生成 26，平均每区块 7279 毫秒，tick 31.20 毫秒；
  • 第 3 次（约 70 秒）：CPU 34.0%，在途 4/4，队列 129，已生成 36，平均每区块 6357 毫秒，tick 36.25 毫秒。

由原始数据可得：CPU 均值约 41.97%，极差 17.6 个百分点；40 秒窗口内生成 22 个区块，吞吐约 0.55 区块每秒；队列从 151 降至 129，消耗速率与吞吐一致，说明没有重复排队或泄漏；tick 最大值 36.25 毫秒，接近但未越过 45 毫秒保护线。

B 组条件为目标 90%、在途上限 16、半径 5、锚点 (4000,4000)、NeoForge 21.1.250。原始数据为：

  • 第 1 次（约 45 秒）：CPU 36.2%，在途 16/16，队列 85，已生成 20，平均每区块 40333 毫秒，tick 0.85 毫秒；
  • 第 2 次（约 65 秒）：CPU 43.4%，在途 16/16，队列 68，已生成 37，平均每区块 29535 毫秒，tick 1.76 毫秒；
  • 第 3 次（约 90 秒）：CPU 53.0%，在途 16/16，队列 37，已生成 68，平均每区块 20207 毫秒，tick 0.85 毫秒。

由原始数据可得：CPU 均值约 44.20%，极差 16.8 个百分点；45 秒窗口内生成 48 个区块，吞吐约 1.07 区块每秒；tick 始终低于 2 毫秒，说明该组条件下主线程几乎没有压力；平均每区块耗时从 40 秒量级降至 20 秒量级，反映的是生成初期需要连带处理邻接区块、随后逐步趋于稳定的过程。

C 组条件为目标 90%、在途上限 4、半径 5、锚点 (6000,6000)、NeoForge 21.1.251。原始数据为：

  • 第 1 次（约 20 秒）：CPU 54.5%，在途 4/4，队列 117，已生成 0，tick 5.06 毫秒；
  • 第 2 次（约 40 秒）：CPU 54.4%，在途 4/4，队列 109，已生成 8，平均每区块 9388 毫秒，tick 41.60 毫秒；
  • 第 3 次（约 60 秒）：CPU 62.1%，在途 4/4，队列 72，已生成 45，平均每区块 2892 毫秒，tick 3.56 毫秒。

由原始数据可得：CPU 均值约 57.00%，极差 7.7 个百分点；40 秒窗口内生成 45 个区块，吞吐约 1.125 区块每秒；tick 出现一次 41.60 毫秒的尖峰，低于保护线但已接近，说明在大量邻接区块同时进入生成时主线程仍会承受短时压力；此外该组首采样时生成计数为 0，说明前 20 秒主要消耗在首批区块的邻接生成准备上。

三组数据放在一起可以读出三个结论。第一，调度器确实在驱动真实工作：生成计数单调增长，队列单调下降，平均每区块耗时随邻接准备完成而下降，没有任何"空转"迹象。第二，进程 CPU 占用并没有逼近目标比例：三组的观测区间为 34% 到 62%，而目标为 80% 或 90%。第三，提高在途上限并不必然提高 CPU：B 组的在途上限是 A 组与 C 组的四倍，但其 CPU 均值（44.2%）反而低于 C 组（57.0%），这既可能来自锚点地形的复杂度差异，也可能来自 21.1.251 与 21.1.250 的补丁差异，本文不把这一差异解释为因果关系，只把它记为需要重复实验的观察。

8.4 静态规模数据

模组自身规模：11 个 Java 文件、1415 行源码、22 个打包条目、jar 体积 29742 字节。作为对照，其依赖的 NeoForge 21.1.251 universal 产物包含 2521 个条目、体积 3551265 字节；userdev 产物包含 963 个条目，其中补丁文件 957 个。这两组数字的比例本身说明了本文的核心论点：一个约 1.4 千行的行为扩展，依附在一个约 3.5 MB、包含近千个补丁的运行时之上；要让前者成立，最经济的方式是保持后者不变，而不是复制后者。

客户端配置的默认值同样构成一组可复现的静态数据：总开关开启，实体剔除距离 128 格，方块实体剔除距离 96 格，统计间隔 1200 tick。注入点在 21.1.250 与 21.1.251 的合并 jar 上均通过描述符核验；两路剔除的活动计数通过统计日志输出，默认每分钟一行。

8.5 数据效度说明

本节数据存在四类效度威胁。其一是单机单次运行，未做重复测量与置信区间估计，CPU 与 tick 的波动可能包含系统噪声。其二是锚点不同导致地形复杂度不同，三组之间无法直接横向比较吞吐。其三是版本差异，C 组运行在 21.1.251 上，与前两组不在同一补丁版本。其四是采样周期为 20 秒，无法捕捉秒级的瞬时波动，tick 的 41.60 毫秒尖峰可能只是被采样恰好捕获的个例。因此本文只把"生成计数增长、队列下降、tick 未越过保护线"视为稳定结论，把"CPU 上限由原版生成执行器并行度决定"视为有数据支持的机制性解释，而把组间吞吐差异视为待复现的观察。

8.6 瓶颈定位的补充分析

三组数据里最反直觉的一点是：B 组的在途上限是 C 组的四倍，CPU 均值却更低。如果调度器是 CPU 的瓶颈，在途上限翻四倍应当带来更高的占用。更合理的解释是，占用由原版区块生成执行器的并行度决定，而 B 组恰好处在一个"生成管线被占满但主线程几乎空闲"的状态：tick 只有 0.85 到 1.76 毫秒，说明主线程没有压力；平均每区块耗时从 40 秒降到 20 秒，说明管线在持续工作；而 CPU 停在 44% 左右，说明还有核心没有被游戏侧的生成任务使用。C 组的 tick 一度达到 41.60 毫秒，说明该组的邻接生成更集中，主线程承担了更多区块应用工作，因此进程 CPU 反而更高。

这一解释可以用一条可操作的判据表达：观察平均每区块耗时与 CPU 的相对变化。当在途增加而平均每区块耗时继续下降时，说明管线还有余量；当在途继续增加而平均每区块耗时上升、CPU 不再上升时，说明已经撞到并行上限，继续加码只会拉长排队。本文的 A 组在第 3 次采样时就出现了这样的信号：在途回到 4/4，但 tick 升至 36.25 毫秒，说明主线程开始承压；此时正确的动作是缩小半径或暂停，而不是继续提高在途。

还需要指出一个与调度器无关的干扰项：进程 CPU 指标包含垃圾回收、区块保存 IO 与网络线程的开销，tick 尖峰也可能由 GC 暂停引起。本文没有采集 GC 日志，因此不能把 41.60 毫秒的尖峰完全归因于区块生成。这一不确定性不影响"tick 未越过保护线"的结论，但会影响对尖峰成因的解释，后续实验应同时采集 GC 日志与区块生成队列长度。

8.7 与既有工具的定性对比

本文没有在同一硬件上对 Chunky 做对照实验，因此不能给出"Stellex 比某工具快多少"的定量结论，任何此类比较都会超出数据支持范围。可以做的是定性对比三个维度。控制维度上，Chunky 一类工具以遍历队列驱动生成，缺少进程 CPU 目标这一层反馈；Stellex 把目标比例、tick 预算与在途上限三者绑定，代价是吞吐可能低于"全速遍历"模式。可观测量上，Chunky 通常报告已完成区块数与进度百分比；Stellex 报告生成数、失败数、平均每区块耗时、tick 与估算 TPS，偏向运行期健康度而非进度。介入深度上，两者都依赖原版生成管线，都没有修改世界数据，因此都不会破坏存档兼容性；差异主要在调度策略而非生成机制。

与 Sodium、Lithium 一类重写型优化相比，Stellex 的能力边界更窄：它不改变区块网格构建方式，不优化 AI 与实体刻，只在渲染调用点做距离剔除。这种窄边界换来了更宽的兼容面，也意味着它不能替代专业优化模组。对整合包作者而言，合理的组合是"专业优化模组负责主要收益，Stellex 负责兜底与可观测性"，而不是把 Stellex 当作帧率问题的唯一答案。

8.8 测量脚本与可复现性

为了保证数据可以被复核，本文的测量没有依赖人工抄写。采样端使用一个约 60 行的 Python RCON 客户端：它按 RCON 协议构造认证包与命令包，认证成功后依次发送 /stellex status，每次读取完整响应并打印，采样间隔 20 秒，最后发送 stop 正常关闭服务端。服务端侧的启动通过 Gradle 的 runServer 任务完成，调度参数经由 JAVA_TOOL_OPTIONS 环境变量注入子 JVM；这一注入方式在 Gradle 守护进程复用时可能失效，因此脚本会先执行一次 gradlew --stop，保证新的守护进程继承环境变量。

可复现性还依赖两个固定条件：世界种子固定为 12345，锚点固定为空白区域坐标，这样同一组参数重复运行时地形复杂度基本一致。日志侧记录了完整的 Done 耗时、模组列表、调度器启动参数与三次状态行，任何读者都可以据此复算均值、极差与吞吐。需要承认的是，脚本没有固定 JVM 堆大小，也没有关闭后台索引等系统服务，这两点都会给 CPU 与 tick 带来额外噪声，属于后续实验应当补齐的控制变量。

8.9 数据汇总

把三组原始数据按同一口径汇总，可以得到一组便于比较的派生指标。A 组 CPU 均值 41.97%，吞吐 0.55 区块每秒，tick 最大值 36.25 毫秒，失败 0；B 组 CPU 均值 44.20%，吞吐 1.07 区块每秒，tick 最大值 1.76 毫秒，失败 0；C 组 CPU 均值 57.00%，吞吐 1.125 区块每秒，tick 最大值 41.60 毫秒，失败 0。三组的失败计数均为零，说明在观测窗口内没有出现票据异常或生成超时；队列消耗速率与生成速率一致，说明计划器、在途集合与完成检测三者之间的记账是自洽的。

从汇总指标看，吞吐与 CPU 之间并不存在单调关系：B 组吞吐约为 A 组的两倍，CPU 只高出约 2 个百分点；C 组吞吐约为 A 组的两倍、与 B 组接近，CPU 却高出约 13 个百分点。这一现象再次说明进程 CPU 受多种因素影响，不能简单用"吞吐越高 CPU 越高"来推断调度效果。派生指标的意义在于提供可复算的中间量，而不是替代对机制的讨论；原始数据与派生指标已随文附上，便于读者自行复算。

9 讨论

9.1 目标百分比应该怎么理解

实验最直接的启示是：把目标百分比说成"承诺占用 N% 的 CPU"是不准确的。调度器采样的是整个 JVM 进程的 CPU 时间，它能做的是在自身工作源允许的范围内朝目标加码，并在超过目标时收缩；但当工作源的并行度被跑满后，继续增加在途任务只会让排队时间变长，不会让 CPU 更忙。因此文档与命令输出应统一表述为"闭环上限"：它保证服务器不会被调度器压垮，也保证空闲算力会被尽量利用，但不保证精确到某个百分点。

这一表述差异对运维很重要。若按"承诺值"理解，容易被误认为调度器失灵；按"上限"理解，则会转而观察平均每区块耗时是否下降，从而判断是否已经撞到并行上限，并据此决定继续加大在途还是缩小半径。

9.2 工作源的可扩展性

当前唯一的工作源是区块预生成，它的优点是收益明确（玩家后续探索更少卡顿）、风险可控（不修改世界数据，只利用原版生成管线）、以及天然可度量。它的局限是并行度受原版执行器约束。若未来需要更高的 CPU 利用率，正确的方向不是增加空转线程，而是引入第二个"真实且可并行"的工作源，例如离线结构索引、配方图预计算或光照数据预生成，并让调度器按优先级与预算在多个工作源之间分配。这样的扩展不会破坏现有兼容性，因为新增工作源仍然运行在模组自己的线程池与公开 API 之上。

9.3 客户端优化的定位

客户端两路剔除的收益来自"看不见却仍在付出渲染代价"的对象，这是低风险的优化面，但它不是帧率的通用解药。Sodium 一类重写型方案收益更高，代价是兼容面更窄；Stellex 选择了窄收益、宽兼容的一端，并通过统计日志让收益可度量。这一取舍适合作为大型整合包的"兜底优化"，而不是替代专业渲染模组。

9.4 与生态的关系

本文反复强调"不改变别人依赖的东西"，这既是兼容性的技术条件，也是生态位的选择。Stellex 不与 Sodium、EntityCulling 争夺渲染管线的控制权，只在它们的空隙里做距离剔除；不与 Connector 争夺转译层的控制权，只使用 Connector 不需要重映射的公开接口；不与加载器争夺元数据与事件时序，只订阅公开事件。这种"少做"的设计使它能与生态共存，也限制了它的能力上限。对本文的目标而言，这一上限是足够的；对未来的扩展而言，这一上限需要被明确认知。

9.5 对"榨干 CPU"话语的反思

"榨干 CPU"是一个很有传播力的说法，但它容易把工程目标引向错误的方向：如果目标是让利用率数字尽可能高，那么最容易的做法是加空转线程，而这恰恰是本文明确拒绝的做法。CPU 是共享资源，与玩家 tick、GC、区块保存、网络线程共同竞争；把利用率推到接近 100% 会让这些路径的延迟变差，最终表现为玩家体感卡顿，而不是性能提升。

更准确的表述是"用有意义的计算填充空闲容量"：调度器只在 tick 有空闲预算时投喂，只在 CPU 低于目标时加码，只在队列非空时工作，队列排空即停机。这三条约束共同保证了"填充"而不是"抢占"。从运维角度，建议把预生成安排在低峰时段，目标设在 60% 到 80% 之间，并在活动高峰用 /stellex pause 停手；这样既利用了闲置算力，又不会与玩家争抢。从能耗角度，避免无意义的高占用本身也是绿色计算的一部分，服务器不需要为"看起来忙"付出电费与散热成本。

9.6 可维护性与长期演进

Stellex 的可维护性建立在规模对比上：约 1.4 千行扩展代码依附于包含近千个补丁的运行时，升级时只需验证扩展本身，而不需要重放运行时。版本迁移的实测也支持这一点：从 21.1.250 迁移到 21.1.251 的全部工作集中在拉取产物、补齐 Gradle 模块元数据与重新构建，源码没有改动一行；构建完成后专用服务端直接启动成功。这说明只要注入点描述符在补丁区间内稳定，迁移成本就停留在构建层面。

长期演进有三个风险点。其一是渲染 API 在 1.21.2 之后的变化，若 LevelRenderer#renderLevel 或方块实体渲染调用被重构，重定向目标会失效；软失败策略会让客户端继续可用，但剔除静默失效。其二是原版区块生成执行器的并行度策略变化，若未来版本改变了后台线程数或票据语义，调度器的闭环参数需要重新标定。其三是 Connector 与优化模组的持续演进，它们可能改变注入点附近的字节码形状，从而影响重定向的匹配。应对方式是把"运行期观测"作为发布流程的一部分：每次升级后跑一遍四种安装组合冒烟，并检查客户端日志中是否存在注入警告与统计行。

在治理层面，本文主张保持零遥测：模组不收集任何玩家数据，不上报任何统计，所有可观测信息只输出到本地日志与命令反馈。这一选择既是隐私要求，也让"性能优化"不被异化为数据采集通道。

10 结论

本文围绕 NeoForge 21.1.x 上的核心模组 Stellex，完成了从形态论证、系统设计、实现到测量的完整闭环。形态论证部分指出，自建内核与完全兼容在六类机制上互斥，兼容性的定义权掌握在第三方字节码手中；系统设计部分给出了事件接线、元数据范围、无通道约束与客户端隔离的具体方案；实现部分给出了票据语义的精确推导、闭环调度算法、完成检测与资源回收策略，以及两路渲染剔除的注入点、判定规则与降级策略。

测量部分报告了三组服务端实验、构建与启动耗时、产物规模与版本迁移过程。实验显示调度器能够在维持 20 TPS 的前提下驱动区块预生成，观测区间内 tick 中位数低于 8 毫秒，最坏 41.6 毫秒；生成吞吐在 0.55 到 1.125 区块每秒之间；进程 CPU 占用稳定在 34% 到 62%，并未逼近设定的目标比例，其上限由原版区块生成执行器的并行度决定。本文据此提出三点实践建议：把目标百分比表述为闭环上限；用平均每区块耗时判断是否撞到并行上限；不要用增加在途任务的方式强行追求更高的 CPU 数字。

未来工作有三个方向：其一，在真实图形环境中测量客户端剔除的帧率收益，并与 Sodium、EntityCulling 做组合对照；其二，在 Connector 环境中用真实 Fabric 模组验证转译链路；其三，引入第二个可并行的工作源，并在多硬件、多版本上重复本文的测量以给出置信区间。

附录 B 术语表

票据（Ticket）：区块系统中表达"某区块需要保持到什么加载等级"的机制，等级越小加载越完整。在途（in-flight）：已经登记票据但尚未完成生成检测的区块数量。闭环上限：调度器以 CPU 采样与 tick 预算为反馈、朝目标比例逼近但不承诺精确达成的控制目标。渲染包围盒（render bounding box）：方块实体渲染器声明的实际绘制范围，可大于方块本体。软失败（soft fail）：注入点无法匹配时记录警告并跳过，而不是让进程崩溃。
