为什么不是内核 fork

Stellex 内核形态与兼容性分析

审计日期：2026-11-21 审计对象：Stellex 的形态选择（NeoForge 核心模组 vs. 自建内核 / 自建发行版） 参考源：work/mcsrc（NeoForge 21.1.248 patched Minecraft 源码）、Gradle 缓存中的 21.1.248 与 21.1.250 userdev jar 作者：Mornfrost Office

1. 要回答的问题

本文回答三件事：为什么"照搬 NeoForge 源码另写内核"与"完整兼容 NeoForge 模组 + Sinytra Connector 转译的 Fabric 模组"在工程上互斥；为什么把 Stellex 做成 NeoForge 上的核心模组是同时满足全部功能与兼容要求的唯一现实形态；以及如果确实需要"发行版"，正确的打包方式应该是什么。

2. 兼容性的定义权不在 Stellex 手里

判断一个模组能不能在某个平台上跑，依据不是平台自己的声明，而是第三方字节码里写死的东西：mixin 配置里的类名、方法名与描述符，AT 引用到的成员，Fabric 模组在 Connector 下的映射目标，FML 的事件时序，mods.toml 里的 loader 依赖。这些目标集合构成了事实上的 ABI。

由此可以写出互斥的证明式：完全兼容意味着第三方字节码的全部目标在运行时仍然存在且语义不变；另写内核意味着这些目标中至少有一类会被替换或移动。两者不能同时为真。要让"另写内核"也完全兼容，唯一办法是让重写后的类、包、方法描述符、AT 结果与事件时序与 NeoForge 逐项一致，而做到这一点在工程上就等于没有重写。因此真正的选择只有"保留 NeoForge 并加行为"或"接受兼容性下降"，中间态不存在。

3. 六条具体机制

3.1 mixin 目标偏移

NeoForge 21.1.248 的 patched 源码有 6317 个 java 文件，NeoForge 自身携带 764 个 patch 文件，其中 186 个文件里有 323 处 // Neo: 补丁标记。这些补丁会改变方法体、局部变量索引与调用序列，而模组的 mixin 往往依赖这些细节。

以 LevelRenderer 为例，NeoForge 的 patch 有 23 个 hunk，向 renderLevel 及各渲染阶段插入了 dispatchRenderStage、isBlockEntityRendererVisible、自定义描边等逻辑。模组常用的 @Inject(at = @At("INVOKE"), target = ...) 多半还能按描述符命中，但 @At("STORE")、@At("TAIL")、@ModifyVariable 的索引与序号、@Redirect 的 ordinal、@Slice 都会随补丁偏移。更直接的失败是调用点数量变化：多一个或少一个目标调用，require = 1 当场报注入错误。

Stellex 自己就是这条规则的例子。LevelRendererMixin 的 @Redirect 依赖 renderLevel 内恰好两处 BlockEntityRenderDispatcher#render 调用（mcsrc 第 1075、1090 行）。内核若增删方块实体渲染路径，这个重定向就会失效或漂移。

3.2 访问转换器（AT）管道

NeoForge 的 META-INF/accesstransformer.cfg 共 545 行（含注释与空行），把原本不可见的成员开放给模组。随手可举的例子：LevelRenderer#shouldShowEntityOutlines() 在第 41 行被改为 public，MinecraftServer.nextTickTimeNanos 在第 169 行被改为 protected，ChunkMap#getVisibleChunkIfPresent(J) 在第 172 行、ServerChunkCache.level 在第 173 行被开放。

模组直接编译到这些开放后的成员上。自建内核若少复刻其中任何一条，依赖它的模组会在运行时抛 NoSuchMethodError 或 IllegalAccessError；若复刻了但作用对象不同，则表现为更隐蔽的行为差异。AT 还决定了 mixin 能访问哪些成员，等于改变了整个可注入面。

3.3 Connector 对 NeoForge 内部的依赖

Sinytra Connector 不是独立运行时，它长在 NeoForge 之上：把 Fabric 模组的字节码映射到 NeoForge/Minecraft 的官方名，转译 Fabric 的 mixin 配置，补齐 Fabric API，并依赖 FML 的事件时序与 mod 元数据。它对 NeoForge 内部的假设一旦被改写，失效的不是"部分功能"，而是整条转译链。

具体到 Stellex：governor 只用了 addRegionTicket/removeRegionTicket/getChunkFuture 这类公开 API，没有碰 ChunkMap 内部；客户端两个 mixin 只打 vanilla 方法。这是 Connector 兼容性能够成立的直接原因——Stellex 没有出现在 Connector 需要重映射或绕过的任何一条路径上。反过来，如果 Stellex 改成自建内核，它就必须同时承担 Connector 的映射目标，而这份目标清单会随 Connector 版本变化，维护成本不可控。

3.4 运行时映射

NeoForge 21.x 的运行时使用 Mojang 官方名，mixin 配置因此可以不带 refmap，模组的 @Inject/@Redirect 直接按描述符匹配运行时类。Stellex 的两个 mixin 都没有 refmap，等于把自己绑在"运行时名等于官方名"这一契约上。自建内核若引入自己的映射层或重命名类，所有不带 refmap 的 mixin 会整体失配，包括 Stellex 自己的两个；若保留官方名，则又与"重写内核"的动机矛盾。

3.5 模组元数据与加载器事件时序

NeoForge 的 MinecraftServer patch 有 26 个 hunk，里面能看到整套时序契约：EventHooks.fireServerTickPre/Post 包住整个 tick、getWorldArray 为世界列表做并发修改保护、handleServerStarted/handleServerStopping 控制生命周期、ServerStatus 里的 modded 标记、以及 synchronizeTime 对 ClientboundCustomSetTimePayload 的 hasChannel 回落。模组在这些时间点上做事，例如在 ServerTickEvent.Post 里做 IO、在 ServerStartedEvent 里初始化。

自建内核一旦改动 tick 边界或事件触发位置，依赖时序的模组行为就会漂移，而且极难归因。Stellex 的做法是只订阅、不拦截：StellexCore.java 第 33-47 行注册的五个监听器全是公开事件，没有替换任何加载器行为。

元数据同理。mods.toml 里 neoforge 依赖 [21.1,21.2) 让所有模组把当前内核当作基座；自建内核若改版本号或 modId，依赖解析会失败，若伪造则 loader 的版本检查与用户升级路径失真。

3.6 维护成本与生态分裂

764 个 patch、953 个加载器 java 文件、545 行 AT，这些是每次 Minecraft 或 NeoForge 升级都要重放的工作量。Connector 与优化模组会持续跟随 NeoForge 内部实现，自建内核永远落后一个版本。用户面对"要兼容就用官方内核、要 Stellex 就不能用某个模组"的二选一时，实际会放弃自建内核。

4. 为什么核心模组形态是唯一解

把 Stellex 做成普通 mods/ 下的 jar，依赖 neoforge，用 @Mod 构造注入加事件总线，不加通道，客户端 mixin 只登记在 client 数组，不改加载器——这套形态满足三件事：

  • 需求 1 的双向 join：协议层没有 Stellex 的必装项，加载器层没有语义改动（细节见 COMPATIBILITY.md 第 2、3 节）。
  • 需求 2 的模组兼容：所有模组、AT、Connector 面对的内核仍然是官方 NeoForge，Stellex 只在其上追加行为。
  • 需求 3 的"可选安装"：服务端不装 Stellex 时客户端功能照常，客户端不装时服务端功能照常，双端独立生效。

代价是能力边界清楚：不能修改 Minecraft 内部语义，服务端只能通过公开区块 API 与事件调度，客户端只能改渲染调用点。这恰好覆盖需求需要的范围，而需求没有要求 Stellex 去改变游戏机制。反过来说，如果把 Stellex 的功能做进内核，它就变成"不可选"的，用户无法只装客户端或只装服务端，需求 1 与需求 3 同时被破坏。

5. 如果确实要做发行版

发行版应该发行"组合"，而不是发行"新内核"。可行的做法：

  • 基座使用 NeoForge 官方安装器产出的服务端与客户端，mods/ 里放 Stellex jar 与用户自选模组，Stellex 通过 neoforge.mods.toml 的依赖声明挂到 21.1.x 上。
  • 服务端提供启动脚本，把调参放进 JVM 参数而不是改代码：-Dstellex.cpu.enabled=true、-Dstellex.cpu.target=60、-Dstellex.cpu.threads=N、-Dstellex.pregen.radius=16、-Dstellex.tps.guard.ms=45、-Dstellex.cpu.integrated=false，以及可选的 -Dstellex.pregen.anchor=<chunkX,chunkZ>（开服前铺出生点，无人时也工作）。JVM 层面可用 -XX:ActiveProcessorCount 控制可用核数，它会同时影响 GovernorSettings.defaultWorkers() 与 vanilla 线程池规模，属于"通过 JVM 参数限制 CPU"的正确落点。
  • 客户端提供 config/stellex-client.properties 模板，默认把方块实体剔除距离设得保守（或按整合包类型给出两套预设），并写明与 EntityCulling 的二选一建议。
  • 分发渠道用 Prism/MultiMC 实例包或 Modrinth/CurseForge 整合包，清单里只列 NeoForge、Stellex 与明确验证过的可选模组；服务端提供压缩包与启动脚本。
  • 明确禁止项：不替换 NeoForge 内核、不改 NeoForge 版本号、不打包改过的 Minecraft 类、不预置 AT、不覆盖 loader 配置、不在未获许可时内置他人的模组 jar。

发布前的检查清单：四种安装组合（普通客户端 + Stellex 服务端、Stellex 客户端 + 普通服务端、双端、双端都不装）各做一次进服冒烟；Connector 环境用一个 Fabric 模组做冒烟；与 Sodium、EntityCulling 各做一次客户端进入世界测试；跑一遍 21.1.x 的版本矩阵；崩溃报告模板里带上 Stellex 版本与 governor 状态行，方便定位。

版本策略上，当前 neoforge.mods.toml 已经把 neoforge 依赖收敛为 [21.1,21.2)，与 minecraft 依赖 [1.21.1,1.21.2) 对齐，这是正确的做法。发布时保持这个范围，不要放宽成 [21.1,)：1.21.2 是渲染与区块 API 发生变化的小版本，放宽会让 loader 允许本模组加载到一个没有验证过的内核上。

6. 结论

互斥性可以写成一句话：完全兼容要求第三方字节码的目标集合不变，另写内核必然改变这个集合，二者不能同时成立。因此"照搬 NeoForge 源码另写内核"不是一条能保住兼容性的路线，它最多能做出一个与 NeoForge 行为相近的新平台，而平台一旦不同，Connector、AT、mixin、事件时序四层里至少有一层会断。

Stellex 的现形态（NeoForge 上的核心模组）是唯一同时满足双向 join、模组兼容、可选安装与新增功能的形态。发行版应在此基础上做"组合分发 + JVM 参数 + 配置模板"，而不是替换内核。

7. 未验证声明

本文引用的是 mcsrc 与 userdev jar 中的源码与 patch 文本，属于离线证据。以下没有验证：Connector 具体版本依赖的内部类清单；Sodium、Iris、Embeddium、ModernFix 等的实际注入点；21.1.251 及以后版本的补丁差异；真实环境下"纯原版客户端连入 NeoForge 服务端"的行为；以及自建内核方案在真实模组集上的失败率（本文只做机制论证，没有做对照实验）。
