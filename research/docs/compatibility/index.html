兼容性审计

Stellex 兼容性审计报告

审计日期：2026-11-21 审计对象：stellex 源码快照（NeoForge 21.1.250 / Minecraft 1.21.1 / Java 21，NeoForge 模组形态） 作者：Mornfrost Office

0. 结论摘要

三条目标路径的设计前提都成立，但成立范围要说清楚。Stellex 没有注册任何自定义 play/config 网络通道，没有改动模组加载器语义，客户端 mixin 只登记在 stellex.mixins.json 的 client 数组里。由此：

  • 普通 NeoForge 客户端进 Stellex 服务端：服务端不存在任何"必须安装 Stellex"的协议项，governor 完全由服务端事件驱动，客户端不需要回包，也不需要安装。
  • Stellex 客户端进普通 NeoForge 服务端：两个客户端 mixin 只改本地渲染调用，不发送任何自定义包，也不请求服务端能力。
  • Stellex 双端：服务端预生成与客户端剔除是两套互不通信的功能，双端同时安装不产生协商分支。

需要提前划清的边界是：loader 本身是否允许某类客户端连入，不由 Stellex 决定。纯原版客户端、以及"NeoForge 服务端是否放行未安装任何模组的客户端"这类问题属于加载器行为，本次离线审计未做实测，统一标注为未验证。

1. 证据基础

本次审计使用三份只读材料：

  • Stellex 源码：src/main/java/com/mornfire/stellex/StellexCore.java、governor/ 下 5 个类、client/ 下 3 个类、mixin/client/ 下 2 个类，以及 src/main/resources/stellex.mixins.json、src/main/resources/META-INF/neoforge.mods.toml。
  • 反编译参考源：work/mcsrc（NeoForge 21.1.248 的 patched Minecraft 源码，6317 个 java 文件，含 META-INF/accesstransformer.cfg 与 net/neoforged 加载器源码）。
  • 版本对比证据：Gradle 缓存中的 neoforge-21.1.248-userdev.jar 与 neoforge-21.1.250-userdev.jar。两者的 764 个 patches/**.java.patch 文件逐字节完全相同（比对脚本输出 identical=764, differing=0）。这意味着本文引用的所有 mcsrc 行号对项目实际依赖的 21.1.250 同样有效。

另外，stellex/build/tmp/createMinecraftArtifacts/nfrt_artifact_manifest.properties 显示项目构建环境使用 FancyModLoader 4.0.44、Mixinextras 0.5.3，与 neoforge.mods.toml 中 loaderVersion = "[4,)" 的声明一致。

2. 协议层：为什么双向兼容成立

FML 在登录与配置阶段交换模组清单与通道声明，其中"必装项"来自每个模组自己注册的 payload。Stellex 的处理方式是让 Stellex 这一项根本不存在：

  • 全部源码中没有 RegisterPayloadHandlersEvent、CustomPacketPayload、PayloadRegistrar、SimpleChannel、PacketDistributor 或 NetworkRegistry 的引用。对 src 全文检索 network/Payload/Channel/Packet 只命中两处：StellexCore.java 第 24 行的说明注释，以及 StellexCommands.java 第 7 行的 net.minecraft.network.chat.Component 导入，两者都不涉及通道注册。
  • 服务端对外能力只有 /stellex 命令（StellexCommands.java 第 21-35 行）。命令树走原版 ClientboundCommandsPacket 下发，属于原版协议，不需要客户端装任何 mod 才能显示；权限用 source.hasPermission(2) 控制，也是原版机制。
  • 客户端没有向服务端请求任何信息：ClientPerfConfig 只读本地 config/stellex-client.properties，StellexClientInit 只订阅 ClientTickEvent.Post（StellexClientInit.java 第 19、34 行），剔除统计只写日志（ClientPerfStats.java 第 94-100 行）。

因此协议层的结论是：Stellex 客户端与服务端之间不存在任何 Stellex 专有握手、版本协商或回包校验。普通 NeoForge 客户端连 Stellex 服务端时，加载器看到的 mod 列表差异里没有 Stellex 的必装通道；Stellex 客户端连普通服务端时，客户端也没有"等不到服务端回包"的路径。这里发挥作用的是"不注册即不参与"这一 FML 行为，而不是任何特殊兼容代码。

一个容易混淆的旁证：NeoForge 自己在 MinecraftServer 的 synchronizeTime 里对 ClientboundCustomSetTimePayload 做了 hasChannel(...) 检查，客户端没有该通道时回落到原版 ClientboundSetTimePacket。这说明 NeoForge 的通道是"按声明可选"的；Stellex 比这更保守，连可选通道都不声明。

3. 加载器层：为什么双向兼容成立

加载器层的关键在于 Stellex 是否改变了模组发现、类加载、AT、事件时序或元数据解析。逐项核对结果如下。

模组元数据没有越界。neoforge.mods.toml 只声明 neoforge 依赖 [21.1,21.2) 与 minecraft 依赖 [1.21.1,1.21.2)，没有 displayTest、features 或自定义 loader 字段；modLoader = "javafml" 与 loaderVersion = "[4,)" 对应 FML 4.0.44。[[mixins]] config = "stellex.mixins.json" 是 NeoForge 官方的 mixin 声明方式，不涉及提前或延后加载。

代码只调用公开入口，不触碰加载器实现。对 net.neoforged.fml 的引用只有四处：ModContainer 与 @Mod（构造注入）在 StellexCore.java 第 6、7 行，FMLPaths（读 config 目录）在 ClientPerfConfig.java 第 11 行，@EventBusSubscriber 在 StellexClientInit.java 第 6 行。没有 ITransformationService、LaunchClassLoader、ModLoadingContext、FMLModContainer 或任何 deobf/Transformer 相关调用。事件全部通过公开事件总线注册：StellexCore.java 第 33-47 行分别监听 ServerStartedEvent、ServerStoppingEvent、ServerTickEvent.Pre、ServerTickEvent.Post、RegisterCommandsEvent。

客户端隔离是硬隔离。stellex.mixins.json 的 mixins 数组为空，client 数组为 ["client.EntityRendererMixin", "client.LevelRendererMixin"]；两个 mixin 类位于 com.mornfire.stellex.mixin.client，包名解析为 com.mornfire.stellex.mixin.client.*。主代码（StellexCore、governor 全部类）没有 import com.mornfire.stellex.client 或 mixin.client，客户端入口靠 @EventBusSubscriber(value = Dist.CLIENT) 在客户端侧自注册。专用服务端因此不会加载 ClientPerfConfig、StellexClientInit 或两个 mixin 类，不会出现 NoClassDefFoundError: net/minecraft/client/...。

服务端功能不要求客户端配合。CpuGovernor 的所有输入来自服务端自身：ServerTickEvent.Pre 记时，ServerTickEvent.Post 读 event.hasTime() 并补充预生成任务（CpuGovernor.java 第 155-192 行），ServerStartedEvent 启动、ServerStoppingEvent 停止。ServerTickEvent.Post#hasTime 在 mcsrc 的 net/neoforged/neoforge/event/tick/ServerTickEvent.java 第 32 行有明确定义，是 NeoForge 21.1 的稳定 API。

4. 三种安装组合的实际行为

普通 NeoForge 客户端 + Stellex 服务端：客户端完全不执行 Stellex 代码。服务端 governor 在 ServerStartedEvent 后启动，只在主世界的目标区块、且 hasTime() 为真时按 tick 预算投递区域票据；有玩家在线时以玩家为中心，没有玩家在线但配置了 -Dstellex.pregen.anchor=<chunkX,chunkZ> 时以锚点为中心，两者都没有则直接返回。/stellex 命令对普通客户端可见可执行（权限等级 2 以上）。客户端的渲染完全走原版。风险面只有服务端行为面（见第 6 节的预生成相关条目）。

Stellex 客户端 + 普通 NeoForge 服务端：governor 不启动，因为 ServerStartedEvent 在客户端只在集成服务器上出现，而 GovernorSettings.integratedServerAllowed() 默认是 false（GovernorSettings.java 第 22 行）。客户端 mixin 照常生效，配置在首次 ClientTickEvent.Post 时从 config/stellex-client.properties 读入，文件不存在时自动写入默认值（ClientPerfConfig.java 第 108-110、170-191 行）。渲染剔除是纯本地决策，不会因服务端没有 Stellex 而报错或降级。

Stellex 双端：服务端预生成与客户端剔除互不通信，各自按本地配置工作。双端都装不会产生额外协议项，也不会出现"客户端等预生成进度"这类联动。若未来要加联动，必须引入通道，这会直接破坏第 2 节的结论，应视为设计红线。

纯原版（vanilla）客户端连 Stellex 服务端：未验证。Stellex 没有新增必装通道，这是不阻断的必要条件，但"NeoForge 服务端是否放行原版客户端"由加载器决定，本次离线环境无法实测。同理，Stellex 客户端连纯原版服务端也不在本设计的承诺范围内。

5. 预生成调度器的能力边界

这一节关系到对外表述是否准确，单独说明。CpuGovernor 的"目标 CPU 百分比"不是硬上限，也不是对主线程的限速：

  • 工作来源只有区块预生成。ChunkPrefetchPlanner 在每个玩家周围 pregenRadius（默认 32，即 65x65 的方框）内挑未加载区块；无人且配置了锚点时，以 -Dstellex.pregen.anchor 给出的区块为中心。CpuGovernor 用自定义 TicketType（CpuGovernor.java 第 49 行）在服务端线程注册票据（第 200 行），工作线程用 getChunkFuture(..., ChunkStatus.FULL, true)（第 281 行）等生成完成，完成后释放票据。
  • 采样与调节是"按可用余量投递"。每 500ms 采样一次进程 CPU（CpuSampler 走 com.sun.management.OperatingSystemMXBean#getProcessCpuLoad），CPU 高于目标 3 个百分点就减少在途上限，低于目标 5 个百分点就增加（第 210-236 行）；tick 超过 tps.guard.ms（默认 45ms）时停止投递。
  • 因此实际效果是"把空闲 CPU 用预生成填到目标值附近"，而不是"把 CPU 压到目标值以下"。当预生成环没有剩余工作、目标维度不是主世界、或既没有玩家也没有配置锚点时，CPU 占用会低于目标值，这是设计使然而非缺陷。反过来，主线程自身的 tick 成本不由 governor 控制，所以它不可能在 TPS 已经吃紧时还保持目标占用。
  • 投递本身仍会产生主线程工作：ServerChunkCache#getChunkFuture（mcsrc net/minecraft/server/level/ServerChunkCache.java 第 211-224 行）对非服务端线程的调用会 supplyAsync 到 mainThreadProcessor，真正执行 getChunkFutureMainThread 的是服务端线程，其中还可能触发 runDistanceManagerUpdates()。所以 CpuGovernor 类注释里"feeding work can never stretch a tick"的说法偏强，准确表述应是"投递量受 hasTime() 与 tick 守卫约束，单 tick 的额外主线程开销有上界，但不是零"。

6. 与常见优化模组、大型模组的冲突矩阵

以下每条只写能从代码或公开机制推出的结论；凡是要看对方模组实际注入点才能确定的，一律标注未验证。

Sodium（NeoForge 版本）：Sodium 重写区块渲染与 LevelRenderer 的渲染路径。Stellex 的 LevelRendererMixin 是 @Redirect 到 BlockEntityRenderDispatcher#render 的两个调用点，只要 Sodium 保留这两个原版调用（它通常保留方块实体渲染），注入就能成功；但 Sodium 对 renderLevel 的大范围改写是否改变这两个调用点的字节码形状，本次无法离线确认。结论：中等风险，未验证，需实测。EntityRendererMixin 的 shouldRender HEAD 注入与 Sodium 没有已知交集，风险低。

Iris（光影）：Iris 依赖 LevelRenderer#renderLevel 的阶段划分，并可能对同一渲染区间做重定向。与 Stellex 的方块实体距离剔除叠加时，光影管线可能拿到不完整的方块实体列表，表现为远处光效缺失或阴影缺块。结论：视觉行为风险，未验证，建议在 Iris 环境下默认关闭方块实体剔除（距离设为 0）。

Embeddium：机制与 Sodium 同类，1.21.1 的可用版本与注入点未验证。结论同 Sodium，需要实测。

EntityCulling：功能与 Stellex 的实体剔除重叠，且它自身会注入实体渲染路径。两者同时启用时，剔除判定叠加，一般只会更早剔除，不会崩溃；但如果它同样 @Redirect 了 BlockEntityRenderDispatcher#render，两个 Redirect 打到同一调用点属于高风险组合（可能出现其中一个静默失效，或 require = 1 直接抛注入失败）。结论：需实测；建议文档里写明"与 EntityCulling 二选一"。

Lithium 及其 NeoForge 移植：影响服务端 tick 与 AI/区块调度。governor 依赖 ServerTickEvent.Post#hasTime() 的语义和区块票据机制，Lithium 若改变 ChunkMap#tick 或距离管理器行为，会改变预生成的推进速度。结论：机制上可共存，性能表现需实测，未验证。

FerriteCore：作用在内存占用（方块状态、模型、NBT 的共享结构），不改渲染调用点，也不改区块票据 API。结论：低风险，无已知交集，未实测。

ModernFix：同时做服务端与客户端优化，注入面很宽，包含渲染与资源加载相关类。与 Stellex 的两个目标没有已知的同一注入点冲突，但它可能改变 LevelRenderer#renderLevel 的执行路径。结论：可共存性未验证，需实测。

Create 及其附属：机械动力系的方块实体渲染常由自有渲染器与 Flywheel 承担，部分可见几何远离方块本体（例如大范围动画、机械臂、列车）。Stellex 的方块实体剔除按方块中心距离判定（LevelRendererMixin.java 第 84-91 行），不读 getRenderBoundingBox，对这类"渲染范围远大于方块本体"的对象有误剔除可能；此外 governor 的额外区块票据会放大 Create 系的区块加载压力。结论：功能可用但需实测，建议在 Create 整合包里把 block_entity_cull_distance 调小或设为 0。

其他区块预生成工具（如 Chunky 类工具）：governor 的票据与它们叠加会造成重复生成、重复 IO，表现为磁盘写放大和内存上涨。结论：不建议同时使用，需实测确认。

服务端地图模组（Dynmap/BlueMap 一类）：它们会主动加载区块渲染地图，与 governor 的票据叠加同样会放大加载量。结论：需实测，默认建议关闭预生成。

6.1 客户端渲染剔除的冲突面（字节码核对）

上面 Sodium、Iris、Embeddium、EntityCulling、Create 五条是依据公开机制的离线推断。本节用本机可取得的 jar 复核了其中能复核的部分，逐条标注为“已从字节码/源码验证”或“需实测”；与上面的表述不一致时以本节为准。核对用到的版本是 Sodium 0.8.13+mc1.21.1、EntityCulling 1.11.3-mc1.21.1、Create 6.0.10，Embeddium、Iris、Flywheel 在本机没有可用的 jar。

  • Sodium（已从字节码验证）：Sodium 的 LevelRendererMixin 在 renderLevel 访问 globalBlockEntities 字段处注入（shift = BEFORE、ordinal = 0），handler 转调 SodiumWorldRenderer.renderBlockEntities(...)；SodiumWorldRenderer 自带 renderBlockEntities、renderGlobalBlockEntities、renderBlockEntity，并在自己的调用点执行 BlockEntityRenderDispatcher.render(...)。原版 LevelRenderer 的两处调用不在 Sodium 的执行路径上，所以 Stellex 的 @Redirect 能正常应用、不会与 Sodium 抢注入点，但运行期基本不会被调用，方块实体窗口计数会长期为 0。实体路径不受影响：Sodium 的实体剔除 mixin 在 EntityRenderer#shouldRender 里用 @WrapOperation 包住 Frustum.isVisible(AABB)，与 Stellex 的 HEAD 注入可以共存。Sodium 0.6.x 未核对（需实测）。
  • Embeddium（需实测）：没有可用 jar。检查三点：启动日志里两个 Stellex mixin 是否报告注入失败；远处方块实体的窗口计数是否恒为 0；关闭 Embeddium 后同一场景的计数是否恢复。只有计数恒为 0 而没有报错时，说明它和 Sodium 一样换掉了 renderLevel 里的调用路径。
  • Iris（需实测）：没有可用 jar。分别开、关光影，观察启动日志有无注入冲突、远处方块实体是否仍被剔除、准星保护是否正常。实体路径不依赖 renderLevel，预期与光影开关无关；方块实体路径取决于 Iris 是否把 renderLevel 的方块实体段包进自己的注入。
  • EntityCulling（已从字节码验证）：WorldRendererMixin 在 LevelRenderer#renderEntity(Entity, double, double, double, float, PoseStack, MultiBufferSource) 的 HEAD 注入并 cancel；BlockEntityRenderDispatcherMixin 在 BlockEntityRenderDispatcher#render(...) 的 HEAD 注入并 cancel；EntityRendererMixin 只做 shouldShowName 与 renderNameTag 的 @Shadow 包装，不碰 shouldRender。结论是职责重叠、目标不冲突：被它先取消的实体不会走到 Stellex，实体统计会偏低；Stellex 放行时它的方块实体检查照常执行，Stellex 跳过时它的检查不执行。两者同时开启不会叠加成两倍收益，做对照时建议先只留 Stellex。
  • Create（已从字节码验证）：Create 自己的 client.LevelRendererMixin 只注入 destroyBlockProgress 与 removeProgress，不改 renderLevel，与 Stellex 不冲突。Create 的方块实体渲染器里有 13 个引用 shouldRenderOffScreen，其中 TrackRenderer 与 StationRenderer 恒返回 true 且 getViewDistance() 为 192，AbstractPulleyRenderer 恒返回 true（视图距离取服务端滑轮绳长配置），BeltRenderer、FlapDisplayRenderer、FluidTankRenderer 在 controller 方块上返回 true。这些对象进入 globalBlockEntities，在纯原版渲染路径下会在 96 到 192 格之间被 Stellex 剔除。Create 6 依赖 Flywheel 做部分可视化，Flywheel 是否让这些渲染器完全绕过 dispatcher.render 未核对（需实测）；如果画面由 Flywheel 渲染，剔除对它们既无收益也无视觉影响，但统计仍会计数。
  • 其他使用 globalBlockEntities 的模组（已从源码验证机制）：shouldRenderOffScreen() 返回 true 的渲染器会被 SectionCompiler 放进全局列表，再在 LevelRenderer 的全局循环里渲染。任何“隔墙或远距离也必须可见”的渲染器都会受方块实体阈值影响；默认没有白名单，需要用户按模组调高距离或设成 0。原版里的同类对象是信标（getViewDistance() 为 256）与末地折跃门（256），因此默认 96 会切掉 96 到 256 格之间的信标光束与折跃门光柱。

6.2 默认值与边界行为（照代码）

配置文件是 config/stellex-client.properties，键名与默认值如下：

  • stellex.client.enabled=true：总开关，关闭后两路剔除都不执行，也不计数。
  • stellex.client.entity_cull_distance=128：实体剔除距离，单位方块，0 表示只关闭这一路。
  • stellex.client.block_entity_cull_distance=96：方块实体剔除距离，单位方块，0 表示只关闭这一路。
  • stellex.client.stats_log_interval_ticks=1200：统计日志间隔，单位客户端 tick，1200 tick 约等于 60 秒。

加载发生在第一个客户端 tick，读取一次后不再读盘，因此改完配置要完全重启客户端才生效。文件不存在时用默认值并写出带英文注释的默认文件；文件存在但读失败时保留默认值并记 WARN，不覆盖原文件；负数距离按 0 处理，日志间隔小于 1 按 1 处理。首个客户端 tick 之前的极少数帧使用内置默认值 128/96。ClientPerfConfig.set(...) 只改内存、不落盘，目前没有命令调用它。

实体这一路的判定顺序是：总开关、距离是否大于 0、entity.noCulling、是否 Player、是否是 Minecraft.player、isCurrentlyGlowing()、getCustomName() != null，最后才比较 entity.distanceToSqr(camX, camY, camZ) 与配置距离的平方。距离用实体自身坐标而不是包围盒；命中时取消整个 shouldRender，后续包围盒与视锥计算都跳过。

方块实体这一路的判定顺序是：总开关、距离是否大于 0、客户端/相机/坐标是否为空、取渲染器的渲染包围盒（BlockEntityRenderer#getRenderBoundingBox，取不到时退回方块本体的 AABB）、相机位置到该包围盒的最近距离平方是否超过阈值；超出后再看 Minecraft.hitResult，只有它是 BlockHitResult 且坐标与当前方块实体相等时才放行。hitResult 为 null、为 MISS、或正指向某个实体时都没有准星保护；保护按客户端 tick 更新后的拾取结果计算。

旁观者模式没有专门分支：玩家实体无论多远都不会被实体剔除，非玩家的普通实体照常按距离剔除；方块实体不区分游戏模式，只认准星保护。跨维度也没有专门状态：每帧都用当前相机位置与当前方块实体坐标现算，统计计数与累计值继续沿用，不随维度切换清零。

统计日志使用名为 stellex-client 的 logger，格式是 Client render culling: {窗口实体数} entities and {窗口方块实体数} block entities culled in the last {间隔} ticks ({累计实体数} and {累计方块实体数} total)。计数器只在 Minecraft.level 非空时推进；总开关关闭且该窗口没有剔除时不打印，总开关打开时即使全为 0 也会打印。累计值从客户端启动累计，代码里的 reset() 当前没有命令入口。

6.3 A/B 实测步骤

先把变量固定住：同一个存档、同一个坐标与朝向、同一个维度，固定渲染距离与模拟距离，用 /time set noon 与 /weather clear 固定环境，关闭光影，只改 stellex-client.properties 一个变量，每次改完完全重启客户端。场景手工布置而不是依赖自然生成：在 96 到 192 格之间放一排箱子或告示牌，在 128 到 256 格之间放几只普通生物，另放一只命名生物和一只发光生物作为必须可见的对照，再准备一处信标或 Create 铁轨观察全局方块实体。

四组对照按顺序做，第二轮反向再做一遍抵消 JIT、GC 与温度的影响：

  • A 组（基线）：enabled=false，远处方块实体与实体都正常渲染。
  • B 组（只开实体）：enabled=true、entity_cull_distance=128、block_entity_cull_distance=0，日志里实体计数应增长、方块实体计数应恒为 0。
  • C 组（只开方块实体）：entity_cull_distance=0、block_entity_cull_distance=96，日志里方块实体计数应增长、实体计数应恒为 0。
  • D 组（全开，默认 128/96）：作为最终体验对照。

想快速确认配置生效，可以先把 stats_log_interval_ticks 调到 100（约 5 秒一条），验证后改回 1200。判断收益来自剔除而不是别的因素，可以按这几条排除：对应那一路的计数必须非零并随视角移动增长，计数为 0 却出现帧率变化说明来源不是剔除；实体计数一直为 0 而远处确有普通生物时，先检查是否装了 EntityCulling 这类会提前取消 renderEntity 的模组，或是否有模组覆写了 shouldRender；方块实体计数一直为 0 而远处确有箱子时，优先怀疑 Sodium/Embeddium 把方块实体渲染搬到了自己的渲染器（Sodium 0.8.13 已从字节码确认）；计数非零但帧率没有变化，说明瓶颈不在方块实体提交，把距离临时调到 16 再测一次，如果变化同样很小就可以排除这条路径。交替做 A→B→A，取多轮中位数，只比较峰值 FPS 会把噪声当成收益。

视觉回归检查：128 格外的命名生物、发光生物和其他玩家应仍然可见；第三人称下自己不会消失；准星对准 96 格外的箱子时它应继续高亮；旁观者模式下飞过 96 格外的 Create 铁轨、车站与信标光束时记录消失距离，与上面的预期区间比对；切一次维度后重复检查，统计不清零属于正常现象。

7. 与 Sinytra Connector 的兼容边界

先把边界分成两半：Connector 负责的部分与 Stellex 不触碰的部分。

Connector 负责：把 Fabric 模组的字节码映射到 NeoForge/Minecraft 官方名，转译 Fabric 的 mixin 配置与 refmap，提供 Fabric API 的 NeoForge 实现，调用 Fabric 的 entrypoint。这些都在 NeoForge 之上运行，Stellex 不参与、也不修改其中任何一步。

Stellex 不触碰：类名与包名（全部在 com.mornfire.stellex.*）、Minecraft 与 NeoForge 的方法签名、AT 管道（不新增也不修改 AT）、加载器事件时序（只订阅，不拦截）、模组元数据格式、网络通道注册、以及区块生成管线内部实现（governor 只用 addRegionTicket/removeRegionTicket/getChunkFuture 这些公开 API）。

由此可以推出：经 Connector 转译的 Fabric 模组，在 Stellex 服务端上拿到的加载器语义与普通 NeoForge 服务端一致，差异只可能来自"区块被更早、更多地加载"这一运行期行为。对客户端而言，Stellex 的 mixin 只改本地渲染调用，不影响 Connector 的转译结果。

需要实测的边界有三处：其一，Connector 对 LevelRenderer、EntityRenderer 这类渲染类可能生成自己的合成 mixin，是否与 Stellex 的两个目标重叠，未验证；其二，Fabric 模组若通过 Connector 注入 ChunkMap/ServerChunkCache，governor 的额外票据会放大其性能开销，属于行为叠加而非注入冲突，未验证；其三，Fabric 模组的 ClientModInitializer 在 Connector 下能否与 Stellex 的 @EventBusSubscriber 共存，取决于 Connector 自身版本，未验证。

8. 升级到 21.1.x 后续版本的风险

本次能给出的最强证据是：21.1.248 与 21.1.250 的 764 个 patch 文件逐字节相同，所以本文与 MIXIN_TARGETS.md 里的行号、签名结论对 21.1.250 直接成立。21.1.251 及以后无法离线核对，只能给出风险排序和自检清单。

风险从高到低：

  • 渲染相关的 mixin 目标被 NeoForge 补丁改写。LevelRenderer#renderLevel 是 NeoForge 注入最密集的方法之一（dispatchRenderStage、isBlockEntityRendererVisible、自定义描边等），补丁更新可能改变方法内调用形状，导致 @Redirect 找不到目标或落到错误的调用点。升级后必须重新核对 renderLevel 内 BlockEntityRenderDispatcher#render 的调用点数量。
  • 服务端区块 API 的公开签名变化。governor 依赖 ServerChunkCache#addRegionTicket(TicketType, ChunkPos, int, T)、removeRegionTicket、getChunkFuture(int, int, ChunkStatus, boolean)、ChunkLevel#byStatus(ChunkStatus)、TicketType#create(String, Comparator)。这些在 21.1.250 的补丁里只有 addRegionTicket 被加了 forceTicks 重载（原 4 参重载保留），但不能保证后续版本不改。
  • ServerTickEvent.Post#hasTime() 语义变化。governor 用它判断"本 tick 还有没有余量"，如果 NeoForge 改变该供应器的来源，"不拖慢 tick"的承诺会失效。
  • neoforge.mods.toml 的 loaderVersion 下限提升。FML 5 出现时 [4,) 会失效，需要同步修改元数据（属于发布流程风险，不是代码风险）。
  • Minecraft 小版本变化（1.21.2+）。此时 BlockEntityRenderDispatcher#render、EntityRenderer#shouldRender 这类签名本身可能变，属于需要重做 mixin 的级别，不在 21.1.x 承诺范围内。

升级自检清单（只读操作，不需要启动游戏）：对比新旧 userdev jar 的 patches/ 是否包含目标文件；对 LevelRenderer、EntityRenderer、BlockEntityRenderDispatcher、ServerChunkCache 的 patch 文本做差异比对；用 javap 检查生产 jar 中三个目标方法的描述符；确认 mixins.json 的 client 数组与类名一致。

9. 无法验证、必须标注的点

  • 纯原版客户端能否连入 NeoForge 21.1 服务端；以及 Stellex 客户端连纯原版服务端的实际表现。这属于加载器行为，本次离线环境没有实测。
  • Sodium、Iris、Embeddium、ModernFix、EntityCulling、Lithium、Create 系、Connector 的实际注入点与共存结果。本文只给机制推断，全部标注未验证。
  • 两个客户端 mixin 在生产环境（非开发映射）下的字节码级匹配。源码级核对已通过（见 MIXIN_TARGETS.md），但没有做 javap 反汇编，也没有启动游戏。
  • 21.1.251 及以后版本的补丁差异。
  • CpuGovernor 的实际 CPU 调节精度与对 TPS 的影响，需要真实服务端压测。
  • Connector 的具体版本要求与 Fabric 模组转译后的 mixin 命名空间，需要实际 Connector 环境验证。

10. 审计发现与处理结果

按当时严重度排序，逐条给出最终处理：

  • 客户端 mixin 的失败策略。已处理：stellex.mixins.json 的 injectors.defaultRequire 由 1 改为 0，注入点被其它模组改变时 Mixin 只记录警告并跳过该注入，客户端不会启动崩溃；代价是该路剔除静默失效，docs/CLIENT.md 已写明看日志与统计行来确认是否生效。
  • 方块实体剔除的判定依据。已处理：改用 BlockEntityRenderer#getRenderBoundingBox，信标光柱、末地折跃门光柱与大型模组多方块结构的渲染包围盒会被正确计入，不会因为方块本体远而整段消失；取不到渲染器或包围盒时退回方块坐标。
  • 实体剔除误伤 Boss。已处理：EnderDragon 与 WitherBoss 显式豁免，不会因为超过 128 格而整只消失。
  • 调度器的记账集合没有回收。已处理：成功路径现在会从 scheduled 移除坐标，done 集合超过 262144 条时整体清空；清空的代价只是后续区块从磁盘读取，不会重新生成。
  • 预生成的默认参数。保留默认半径 32，但在 docs/TUNING.md 写明了半径与面积、磁盘占用、低配服务端的收敛建议；README.md 给出保守的起步参数。
  • CPU 目标的对外表述。已处理：README、TUNING 与 /stellex status 的措辞统一为"本 JVM 进程 CPU 的目标百分比"，并明确它是闭环目标而不是硬限制。
  • 与 EntityCulling 的关系。已处理：docs/CLIENT.md 与本文第 6.1 节统一口径为职责重叠、目标不冲突但收益不叠加，建议二选一或按 A/B 步骤对照。
  • 类注释过强。已处理：CpuGovernor 的注释已改为承认非主线程请求 getChunkFuture 仍会在主线程产生记账开销，并说明 in-flight 上限与 TPS 保护就是用来兜住这部分开销的。

仍然遗留、需要在真实环境验证的风险：Sodium/Embeddium/Iris/Flywheel 的注入路径与剔除收益（第 6.1 节已标注证据等级）、Connector 具体版本的转译行为、21.1.251 及以后版本的补丁差异、以及目标 CPU 百分比在实际负载下的收敛精度。

11. 结论

Stellex 现阶段的兼容性成立依据是"少做"而不是"多做"：没有自定义通道、没有加载器改动、没有服务端与客户端之间的隐含约定，客户端逻辑在物理客户端侧被隔离。这套设计对普通 NeoForge 双端互通是成立的；对 Sinytra Connector 的兼容性建立在"不触碰 Connector 与 NeoForge 的契约"之上，边界清晰但需要实测兜底。真正需要修正的是表述与默认值，而不是架构方向。
