客户端渲染优化

客户端渲染优化说明

Stellex 客户端的优化全部是可开关、可测量的两路剔除。它们不修改区块渲染管线，不替换 Sodium/Iris，也不改变任何模型的绘制结果，只在"这个对象反正看不见"时提前返回。默认值经过保守选择：宁可少剔一点，也不要出现"远处的箱子突然消失"这种事。

配置文件

路径是 config/stellex-client.properties。文件第一次加载时如果不存在，会自动写出带英文注释的默认值。所有键都带 stellex.client. 前缀：

  • stellex.client.enabled=true：总开关。设成 false 后两路剔除都停止，计数也不再增加。
  • stellex.client.entity_cull_distance=128：实体剔除距离（方块）。超过这个距离、且没有自定义名称、没有发光、不是玩家、不是本地玩家、并且 noCulling 为假的实体直接跳过渲染。设成 0 关闭这一路。
  • stellex.client.block_entity_cull_distance=96：方块实体剔除距离（方块）。以渲染器自己的渲染包围盒（BlockEntityRenderer#getRenderBoundingBox，取不到时退回方块本体）到相机的最近距离计算，因此信标光柱这类大范围渲染对象按它实际绘制的范围判定。准星指向的方块实体永远不剔除。设成 0 关闭这一路。
  • stellex.client.stats_log_interval_ticks=1200：统计日志间隔（客户端 tick）。1200 tick 约等于 1 分钟。负数或 0 会被修正为 1。

配置文件在第一个客户端 tick 时加载一次。改动后需要重启客户端才会生效，没有热重载。

行为边界

以下边界是按当前代码实现写的，不是推测：

  • 跨维度时 Minecraft.level 会切换，但剔除距离只与当前相机位置有关，因此不需要特殊处理。
  • 旁观者模式的玩家实体同样属于 Player，不会被剔除。
  • 实体剔除不区分生物与掉落物、船、矿车等，只要满足条件一律剔除；需要近距离观察某些实体时可以临时把距离调大或把总开关关掉。
  • 方块实体剔除对 globalBlockEntities 同样生效，也就是说某些模组注册为"全局渲染"的方块实体也在剔除范围内。如果某个模组的全局方块实体必须远处可见，把 block_entity_cull_distance 设成 0。
  • 被剔除的对象不会触发它们的渲染器，所以也不会触发渲染器内部的副作用（例如某些模组在渲染时更新缓存）。这是性能收益的来源，也是某些模组表现异常时需要优先排查的点。

统计日志

客户端日志里每隔配置的 tick 数会出现一行：

Client render culling: 1234 entities and 56 block entities culled in the last 1200 ticks (98765 and 4321 total)

括号外是窗口值，括号内是累计值。如果两个窗口值都长期为 0，说明当前场景下剔除没有命中，收益为零，可以关掉以免浪费一次距离计算。

A/B 实测方法

想确认帧率变化是否真的来自 Stellex，请按下面顺序做一次对照，不要凭感觉：

  1. 固定场景：站在同一个位置，面向同一方向，保持实体与方块实体数量稳定（例如在基地中央、周围有大量箱子与生物）。
  2. 记录基线：把 enabled 设为 false，用 F3 的帧率或外部工具记录 60 秒的平均帧时间。
  3. 打开实体剔除：只把 enabled 设为 true，block_entity_cull_distance 设为 0，同样位置记录 60 秒。
  4. 打开方块实体剔除：再把 block_entity_cull_distance 设回 96，记录 60 秒。
  5. 对比三组数据的平均帧时间与 1% low，同时查看日志里两类剔除各自的窗口计数。计数为 0 的那一路不会带来收益。

需要注意，帧率还会受粒子、阴影、区块加载、GC 影响，单次测量波动可能达到 10% 以上，建议每组至少测两次取中位数。

与其它优化模组的关系

  • Sodium/Iris/Embeddium 会重写大量的区块与实体渲染路径。Stellex 的注入点是 EntityRenderer#shouldRender 与 LevelRenderer#renderLevel 内部的 BlockEntityRenderDispatcher#render 调用点，理论上与这些模组共存，但 Sodium 一系对 renderLevel 有整体改写时，@Redirect 可能找不到目标而报错。出现这种情况请先把本文档的 A/B 步骤走一遍确认是 Stellex 导致的，再考虑暂时关闭。
  • EntityCulling 做的是遮挡剔除与更激进的视锥剔除，与 Stellex 的距离剔除职责有重叠。两者同时开启理论上不冲突，但如果 EntityCulling 也重定向了 BlockEntityRenderDispatcher#render，两个 @Redirect 会争用同一个调用点，表现为其中一方静默失效。这种组合属于需要实测的高风险项，建议先只开一方做对照。
  • Stellex 的 stellex.mixins.json 把 injectors.defaultRequire 设为 0：如果某个注入点因为与其他模组冲突而找不到目标，Mixin 只记录警告并跳过该注入，不会让客户端启动崩溃。代价是这种情况下该路剔除静默失效，确认是否生效请看日志里的警告与统计行。
  • 如果整合包已经包含成熟的渲染优化组合，建议先关闭 Stellex 的两路剔除跑一局，确认没有视觉回归后再逐项打开。
