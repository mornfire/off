Mixin 目标核对

Stellex Mixin 目标核对报告

审计日期：2026-11-21 审计对象：com.mornfire.stellex.mixin.client 下的两个客户端 mixin 与 src/main/resources/stellex.mixins.json 参考源：work/mcsrc（NeoForge 21.1.248 patched Minecraft 源码）；项目依赖 NeoForge 21.1.250 作者：Mornfrost Office

1. 审计基线与方法

本报告的核对方式是源码级：在 mcsrc 中定位目标类与目标方法，记录方法声明的行号、参数类型、返回类型，再按 Java 泛型擦除规则写出描述符，与 mixin 注解里写的 method/target 逐字符比对；随后检查 NeoForge 的 patches/ 里是否改过这些方法，作为稳定性判断依据。没有做 javap 反汇编，也没有启动游戏，这两项列在"待复核"里。

版本可比性有一条硬证据：Gradle 缓存中的 neoforge-21.1.248-userdev.jar 与 neoforge-21.1.250-userdev.jar 的 764 个 patch 文件逐字节相同。因此 mcsrc 的行号与签名可以直接用于 21.1.250。

2. 现状

当前仓库有且只有两个 mixin 类，都在 src/main/java/com/mornfire/stellex/mixin/client/：

  • EntityRendererMixin.java，@Mixin(EntityRenderer.class)，一个 @Inject。
  • LevelRendererMixin.java，@Mixin(LevelRenderer.class)，一个 @Redirect。

stellex.mixins.json 的内容为：required: true、package: com.mornfire.stellex.mixin、compatibilityLevel: JAVA_21、minVersion: 0.8、mixins: []、client: ["client.EntityRendererMixin", "client.LevelRendererMixin"]、injectors.defaultRequire: 0。neoforge.mods.toml 第 26-27 行声明了 [[mixins]] config = "stellex.mixins.json"。

两个 mixin 的类名只出现在 mixins.json 与各自的 package 声明里，主代码没有任何 import 或实例化。这一项检查通过。

3. 目标一：EntityRenderer#shouldRender

目标类与方法：net.minecraft.client.renderer.entity.EntityRenderer#shouldRender。mcsrc 证据：net/minecraft/client/renderer/entity/EntityRenderer.java 第 52 行，

public boolean shouldRender(T p_114491_, Frustum p_114492_, double p_114493_, double p_114494_, double p_114495_)

T 的界在类声明 EntityRenderer<T extends Entity>（同文件第 26 行）上，擦除后参数类型为 net.minecraft.world.entity.Entity。完整描述符：

(Lnet/minecraft/world/entity/Entity;Lnet/minecraft/client/renderer/culling/Frustum;DDD)Z

mixin 侧写的是 @Inject(method = "shouldRender", at = @At("HEAD"), cancellable = true)，handler 参数为 Entity、Frustum、三个 double、CallbackInfoReturnable<Boolean>。类型与顺序完全匹配，返回类型 Z 与 CallbackInfoReturnable<Boolean> 匹配。方法名 shouldRender 在该类中没有重载（同文件只有第 89 行的 render），不存在歧义。

稳定性判断：EntityRenderer.java 确实在 NeoForge 的 patch 列表里，但补丁只改了两处，分别是 render 方法末尾的名牌事件（patch 中 @@ -94 附近）和 renderNameTag 的距离判断（@@ -181 附近），没有触及第 52 行的 shouldRender。同时 neoforge.mods.toml 的依赖下限是 [21.1,21.2)，且 21.1.248 与 21.1.250 的 patch 全等。结论：这是原版（vanilla）方法，在 21.1.x 内属于稳定签名。

行为边界：vanilla 里覆盖 shouldRender(T, Frustum, double, double, double) 的渲染器有三个（EndCrystalRenderer 第 108 行、GuardianRenderer 第 36 行、ShulkerRenderer 第 39 行）；ElytraLayer 与 BeaconRenderer 里的同名方法参数不同，不构成覆盖。前三个都显式调用 super.shouldRender(...)，所以 HEAD 注入会参与判定：setReturnValue(false) 会让 super 返回 false，但子类仍可能通过 || getBeamTarget() != null 之类的逻辑返回 true，行为是"可能少剔除，不会多剔除"。modded 渲染器若覆盖 shouldRender 且不调用 super，则完全绕过 Stellex 的剔除，属于安全的降级。

另一处语义差异需要记录：HEAD 注入发生在 entity.shouldRender(x, y, z) 与视锥判断之前（mcsrc 同文件第 53 行是 entity.shouldRender），被剔除的实体同时跳过了这两步。对原版实体这不是问题，但若某个模组实体在 Entity#shouldRender 里做了副作用（例如按距离调整状态），会被跳过。当前 handler 只对超过 entity_cull_distance（默认 128）的实体动手，影响面有界。同样的距离判定也作用于末影龙、凋灵一类大型 BOSS 实体，它们没有 noCulling 标记，超过阈值时会整只消失；需要在远处看到 BOSS 的场景应调大阈值或关闭这一路。

4. 目标二：LevelRenderer#renderLevel 的 BlockEntityRenderDispatcher#render 重定向

目标类与方法：net.minecraft.client.renderer.LevelRenderer#renderLevel。mcsrc 证据：net/minecraft/client/renderer/LevelRenderer.java 第 914-916 行，

public void renderLevel(DeltaTracker p_348530_, boolean p_109603_, Camera p_109604_, GameRenderer p_109605_,
        LightTexture p_109606_, Matrix4f p_254120_, Matrix4f p_323920_)

DeltaTracker 的包是 net.minecraft.client.DeltaTracker（同文件第 48 行 import）。描述符：

(Lnet/minecraft/client/DeltaTracker;ZLnet/minecraft/client/Camera;Lnet/minecraft/client/renderer/GameRenderer;Lnet/minecraft/client/renderer/LightTexture;Lorg/joml/Matrix4f;Lorg/joml/Matrix4f;)V

重定向目标：BlockEntityRenderDispatcher#render。mcsrc 证据：net/minecraft/client/renderer/blockentity/BlockEntityRenderDispatcher.java 第 69 行，

public <E extends BlockEntity> void render(E p_112268_, float p_112269_, PoseStack p_112270_, MultiBufferSource p_112271_)

擦除后为 (Lnet/minecraft/world/level/block/entity/BlockEntity;FLcom/mojang/blaze3d/vertex/PoseStack;Lnet/minecraft/client/renderer/MultiBufferSource;)V，与 mixin 里 At 的 target 字符串逐字符一致。BlockEntityRenderDispatcher.java 不在 NeoForge 的 patch 列表中（userdev jar 中无对应 patch 文件），render 是纯 vanilla 方法，稳定性最高。

调用点核对：renderLevel 内共有两处 this.blockEntityRenderDispatcher.render(...)，分别在 mcsrc 第 1075 行与第 1090 行，对应"可见 section 遍历"和"global block entities 遍历"两个循环。两处调用之前各有一行 NeoForge 守卫 ClientHooks.isBlockEntityRendererVisible(...)（第 1052、1083 行），重定向位于守卫之后，这一点与 client-perf-dev 的自述一致。@Redirect 没有写 ordinal 也没有切片，作用于该方法的全部匹配调用点，正好覆盖这两处。

稳定性判断：LevelRenderer 是 NeoForge 注入最密集的类之一，patch 有 23 个 hunk，其中 @@ -1051,6 +_,9 @@ 与 @@ -1060,9 +_,13 @@ 正是给这两个循环插入 isBlockEntityRendererVisible 守卫的位置。关键点在于：补丁只在这些调用之前插入了 continue 守卫，INVOKE BlockEntityRenderDispatcher.render 指令本身仍是原版调用，没有被包裹或替换，因此 @Redirect 的目标在 21.1.248 与 21.1.250 上都能命中。这个方法在 21.1.x 内属于"补丁内但调用点稳定"，升级时需要重新核对（见第 7 节）。

行为边界：判定依据是方块实体的 getBlockPos() 中心到相机的距离（LevelRendererMixin.java 第 84-91 行），不是渲染包围盒。对渲染范围远大于方块本体的对象（信标光束、部分模组机器、Create 系的大范围动画）存在误剔除可能。vanilla 的 BeaconRenderer 光柱从方块本体向上延伸很远，玩家站在 96 格外看光柱时会被整段剔除，这是可复现的视觉差异，建议实测后决定是否豁免。

5. 配置与侧隔离核对

stellex.mixins.json 的侧隔离是本次审计的重点项，结论通过：

  • mixins 数组为空，专用服务端不会应用任何 mixin。
  • 两个条目都在 client 数组，且 required: true 只对 config 生效；client 列表在服务端被 Mixin 跳过，不会加载 com.mornfire.stellex.mixin.client.*，因此不会因为引用 net.minecraft.client.* 而报 NoClassDefFoundError。
  • 两个 mixin 只单向 import com.mornfire.stellex.client 包，client 包不反向引用 mixin；StellexCore 与 governor 包不引用这两者。
  • mixin 配置没有 refmap 字段。NeoForge 21.x 运行时使用 Mojang 官方名，config 中的字面名可直接匹配；这一点在本地没有生产环境实测，标注为待复核。

required: true 加 injectors.defaultRequire: 0 的组合是本项目采用的决定：任何一个注入点匹配失败时，Mixin 只记录警告并跳过该注入，客户端不会因此崩溃。代价是该路剔除静默失效，因此统计日志与警告都要一起看。这个决定的具体权衡见 COMPATIBILITY.md 第 10 节。

6. 审计发现

  • 目标不匹配：没有发现。两个 mixin 的类、方法、描述符在源码级全部对上，泛型擦除也与 handler 参数一致。
  • 通道残留：没有发现。src 全文没有自定义 payload、channel 或 packet 注册，唯一与 network 相关的引用是 net.minecraft.network.chat.Component。
  • 加载器语义改动：没有发现。对 net.neoforged.fml 的引用只有 ModContainer、@Mod、FMLPaths、@EventBusSubscriber 四个公开入口。
  • 方块实体剔除的判定依据偏弱：按方块中心距离判定，未用 BlockEntityRenderer#getRenderBoundingBox。NeoForge 的 ClientHooks.isBlockEntityRendererVisible 用的就是渲染包围盒加视锥，建议 Stellex 与之对齐或在默认配置里对信标类对象豁免。
  • 服务端侧的同类问题（供交叉参考）：CpuGovernor 的"目标 CPU 百分比"只调节预生成并发，不是主线程限速，也不保证在无工作时维持目标占用；对外表述需要收紧，细节在 COMPATIBILITY.md 第 5 节。
  • 统计日志默认每 1200 tick（约一分钟）输出一行 INFO，长期挂机或接入日志聚合时，日志文件会持续增长；建议默认关掉或把间隔调大。

7. 待复核清单与证据要求

下面每一项都需要在真实的 NeoForge 21.1.250 开发环境补一次证据，任一项不通过都要回到实现层修正。

  • 字节码级描述符：对生产 jar 里的 net/minecraft/client/renderer/entity/EntityRenderer.class、net/minecraft/client/renderer/LevelRenderer.class、net/minecraft/client/renderer/blockentity/BlockEntityRenderDispatcher.class 执行 javap -p -s，确认 shouldRender、renderLevel、render 的描述符与本文一致。验收标准：描述符字符串逐字符相同。
  • 注入点数量：client-perf-dev 提到的"字节码偏移 1586 与 1739"本次没有复核。要求提供 renderLevel 内两处 invokevirtual BlockEntityRenderDispatcher.render 的字节码偏移与数量，确认 @Redirect 实际命中两处且没有第三处。验收标准：Mixin 导出报告或 -Dmixin.debug.export=true 后的 class 文件里能看到两次重定向。
  • 注入生效性：启动客户端时用 -Dmixin.debug=true，确认两个 mixin 都 Mixin apply 成功，且 stderr 没有 InjectionError。
  • 侧隔离：以专用服务端启动，确认日志没有 stellex.mixins.json 的 client mixin 应用记录，也没有 NoClassDefFoundError。
  • 与优化模组的共存：至少验证 Sodium（NeoForge 版）与 EntityCulling 两种组合下客户端能否正常进入世界、LevelRenderer 的 @Redirect 是否仍命中。验收标准：进入世界无崩溃，客户端日志出现剔除统计。
  • 视觉回归：信标光柱、末地水晶光束、Create 系大范围渲染对象在 96 格外的可见性；确认误剔除范围后决定是否改为渲染包围盒判定。
  • 升级回归：每次升级 NeoForge 后重跑第 1 节的 patch 对比与第 7 节的 javap 检查。

8. 未验证声明

本文的"目标存在、描述符匹配、补丁未改动"都是源码级结论，依据是 mcsrc 与 userdev jar 中的 patch 文本。以下没有验证：生产运行时的字节码匹配；refmap 缺省在 NeoForge 21.1 生产环境的行为；两个 mixin 与 Sodium、Iris、Embeddium、EntityCulling、ModernFix 等模组的实际共存；21.1.251 及以后版本的补丁差异。
