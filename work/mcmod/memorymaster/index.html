MemoryMaster

NeoForge 1.21.1 服务端 · 1.0.0

给服务端省内存的。七个模块能单独关，注入失败会自动退回原版行为，慌了还有一条 /mmcmf panic 兜底。

给服务端省内存的。

为什么做它

服务器跑久了，堆内存会慢慢涨上去：区块缓存、实体索引、掉落物、AI 目标的中间对象，很多都是"用完就忘"的结构。原版并不是没有回收，而是回收得偏保守——它优先保证正确性，不会为了省内存去做激进裁剪。

MemoryMaster 的思路是：在不改变游戏行为的前提下，替服务端做那些"可以更早释放"的清理。

它是怎么运作的

模组由 7 个独立模块组成，默认全开，可以逐个关闭：

  • 每个模块有独立的 mixin 文件，互不牵连
  • 注入前由 MixinConfigPlugin 校验目标类与目标成员是否存在
  • 所有注入都使用 require = 0，目标不存在时静默跳过，不会让服务端起不来
  • 每个模块的优化逻辑都包在 try-catch 里，异常时降级为原版行为
  • 首次加载会做两段式自检，把环境信息写进日志

这种"处处留退路"的写法看起来很啰嗦，但服务端模组的第一原则是不添乱：宁可少优化一点，也不能因为一次注入失败把整个服务器拖下水。

配置在 config/mmcmf-*.toml，每个模块一个开关。想快速回退可以用 /mmcmf panic，它会关闭全部模块并提示重启。

怎么用

只装服务端即可，客户端不需要。建议流程：

  1. 先全开跑一段时间，观察 MSPT 和堆占用曲线
  2. 如果出现异常（实体行为不对、区块加载异常），用 /mmcmf panic 回退
  3. 再逐个打开模块，定位是哪一个引起的

不要和同类"内存优化"模组叠装，尤其是都改区块/实体生命周期的——两个模组各自正确，叠加起来不一定正确。

取舍与边界

不做激进裁剪。没有"自动卸载远处区块"这类操作，那会影响玩家体验（回头看不见自己建的房子）。

不做统计面板。它只优化，不提供花哨的仪表盘；要看数据用 Spark 之类的工具。

默认全开但要能全关。这是一个态度问题：优化应该是可撤销的，而不是一次性的赌博。

版本与依赖

当前 1.0.0。NeoForge 1.21.1 服务端 / Java 21，无前置，MIT 协议。因为全部使用 require = 0 与降级逻辑，理论上可以和其他服务端模组共存；如果目标类被其他模组改过，注入会跳过而不是报错。

观察与调参

优化类模组最大的风险是"看起来有效，实际只是把问题推后"。建议的观察方式是：

  • 用 Spark 或类似工具看 MSPT 的分布，而不是只看平均值
  • 观察堆占用曲线是否仍然持续上涨（如果还在涨，说明瓶颈不在被优化的部分）
  • 关注 GC 频率与停顿时间，这两个指标比堆大小更能反映真实体验

调参顺序建议从"最安全"的模块开始：先开只影响缓存的，再开涉及实体生命周期的，最后开涉及区块数据的。每开一个跑一段时间，出问题就关掉回退，定位清楚再继续。

/mmcmf panic 是最后一道保险：一键关闭全部模块并提示重启。它的意义不是"优化失败"，而是让服主在半夜出问题时有一个确定能恢复的操作。

兼容性说明

因为注入使用 require = 0 且注入前校验目标存在，理论上不会因为目标缺失而崩服。但如果另一个模组也改同一处逻辑，双方的注入顺序会决定最终行为——这种冲突无法自动检测，只能靠实际运行观察。建议不要和其他"内存优化/区块优化"模组叠装。

什么时候不该用它

如果服务器的瓶颈是磁盘 IO、网络带宽或者某个具体模组的死循环，内存优化帮不上忙，反而会掩盖问题。先用 Spark 定位，再决定要不要装。

另外，开发环境与本地测试不建议开：它会改变对象生命周期，某些依赖"晚回收"行为的调试逻辑可能表现异常。
