KIPL · Kill Inspector

NeoForge 1.21.1 服务端 · 1.0.0

想知道谁杀了谁。输入 /kipl，它会告诉你最近一次击杀的时间、地点，以及是游戏事件还是控制台日志抓到的。

想知道谁杀了谁。输入 /kipl 就知道了。

为什么做它

服务器上出现"我明明没死，东西怎么没了"的争论时，最缺的是证据。原版的死亡信息只出现在聊天栏，刷屏之后就找不到了；控制台日志有记录，但要翻很久。

KIPL 把这件事做成一条指令：/kipl，直接告诉你最近一次玩家击杀的时间、地点和判定渠道。

它是怎么运作的

模组同时开两条检测通道：

  • 游戏内事件：监听 LivingDeathEvent，拿到击杀者、被击杀者、维度与坐标
  • 控制台日志：解析服务端日志里的死亡消息，作为事件通道的补充

两条通道互相印证：如果事件通道因为其他模组取消/改写事件而漏掉，日志通道还能兜底；如果日志被其他插件改写，事件通道仍然有效。

输出包含：时间（含"几分钟前"的相对时间）、地点（维度 + 坐标）、渠道（事件 / 控制台 / 两者一致）。

怎么用

装服务端即可。玩家（或管理员）输入 /kipl，返回最近一次玩家击杀记录。如果最近没有击杀，会提示"没有记录"。

可以配合权限插件限制指令使用者的权限等级——模组本身不做权限判断，交给服务端。

取舍与边界

只记录玩家击杀玩家。怪物击杀、环境死亡不在范围内，那些用原版日志就够了。

不存历史。只保留"最近一次"，不做数据库。需要长期记录请用日志系统。

不做回放。没有死亡回放、没有物品追溯，只回答"谁杀了谁"。

版本与依赖

当前 1.0.0。NeoForge 1.21.1 服务端 / Java 21，无前置，MIT 协议。日志解析依赖原版死亡消息格式，如果服务器装了修改死亡消息的模组，日志通道可能失效，事件通道仍然可用。

排查流程

实际使用中，KIPL 最常见的场景是"物品丢失"纠纷。推荐的排查顺序：

  1. 先 /kipl 看最近一次击杀，确认死亡是否由玩家造成
  2. 如果不是玩家击杀，看服务端日志里的死亡消息（掉落、岩浆、虚空）
  3. 如果是玩家击杀，再确认击杀发生的位置是否在安全区/领地内
  4. 需要更详细的信息时，对照日志时间戳

/kipl 只回答"谁杀了谁"，不回答"为什么"。所以它更适合作为第一步，快速排除或确认"玩家击杀"这个可能性。

为什么用双通道

只监听事件的问题是：其他模组可能取消或改写 LivingDeathEvent，导致记录丢失。只看日志的问题是：日志会被插件改写格式，解析容易失败。两条通道同时开，任意一条有效就能给出答案；两条一致时可信度最高。

如果两条通道给出的结果不一致（时间或击杀者不同），通常意味着事件被中途修改过，这时候日志的原始记录更接近事实。

记录能保存多久

只有最近一次击杀。服务器重启后记录会清空，不会落盘。这是刻意的：它是个排查工具，不是审计系统；如果要长期留痕，请用日志收集或专门的审计插件。

如果需要在重启后仍然可查，可以在服务端日志里搜索死亡消息，KIPL 的日志通道解析的就是这个格式。

为什么不做成 GUI

指令输出最直接：管理员在聊天栏里就能看到结果，不需要打开界面，也不需要客户端装东西。做成 GUI 反而会引入客户端同步、权限判断、界面语言等问题。

如果你希望有更丰富的展示，可以把指令输出接到服务端日志或者机器人里，KIPL 的输出格式是稳定的文本。
