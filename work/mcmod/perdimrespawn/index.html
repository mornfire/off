Per-Dimension Respawn

NeoForge 1.21.1 服务端 · 1.0.0

原版只有一个出生点，在地狱放个重生锚就把主世界的床盖掉了。这个模组让每个维度各记各的，死在哪就回哪。

原版只有一个出生点，这个模组让每个维度各记各的。

为什么做它

原版的出生点系统只有一个全局槽位：respawnPosition 加 respawnDimension。你在主世界床边睡一觉，出生点记在主世界；去地狱放个重生锚并激活，出生点就被覆盖成地狱；再回主世界睡觉，又覆盖回来。

单人玩还能忍，服务器上就很致命：玩家在下界建基地、设了重生锚，回主世界睡一觉，再死在下界就回不到自己的锚了。

它是怎么运作的

模组把"出生点"从单槽位改成按维度分别存储的映射：

  • 每个维度独立记录该维度下的重生点坐标与朝向
  • 死亡时按死亡所在维度查找对应记录
  • 如果该维度没有记录，退回原版逻辑（世界出生点）

同时处理了几种边界情况：

  • 重生锚在地狱的有效性判定保持原版
  • 床在主世界以外维度会爆炸，这个行为不变
  • 玩家跨维度传送（传送门、指令）不会污染出生点数据

怎么用

只装服务端即可。玩家在任意维度设置出生点（床、重生锚、指令），模组会自动按维度归档。

服务器建议：

  • 和"随机重生""死亡不掉落"这类插件共存时，确认它们的重生逻辑优先级
  • 如果用了多世界插件，需要确认插件世界的维度 key 能被识别
  • 数据存在玩家 NBT 里，跨服同步（如果用了跨服插件）需要额外处理

取舍与边界

不改变原版规则。床在地狱还是会爆，重生锚在主世界还是无效——模组只解决"记录"问题，不解决"合法性"问题。

不做传送。死亡后只是在对应维度的出生点重生，不会把你跨维度拉回去。

数据在玩家身上。不写全局配置文件，所以卸载模组后原版会退回到单槽位逻辑，已记录的其他维度出生点会丢失。

版本与依赖

当前 1.0.0。NeoForge 1.21.1 服务端 / Java 21，无前置，MIT 协议。与大多数出生点相关模组冲突（都改同一处逻辑），装之前先确认没有重复功能。

多世界与代理环境

模组按维度 key 记录出生点，所以多世界插件创建的世界也能正常使用——前提是这些世界的维度 key 是稳定的，不会每次重启都变。部分插件会动态生成世界名，那种情况下记录会失效，表现为"死亡后回到世界出生点"。

如果服务器用了 BungeeCord/Velocity 之类的代理，玩家在不同子服之间切换，出生点数据是跟着玩家存档走的。子服之间不共享存档时（常见于大厅+生存分离的架构），出生点只在当前子服有效，这是预期行为。

数据与迁移

出生点数据存在玩家 NBT 的自定义字段里，不写全局配置。升级模组版本时会保留旧字段，读取时优先用新结构，找不到再回退。

卸载模组后，原版会退回到单槽位逻辑，其他维度的记录仍然留在 NBT 里但不会再被读取。重新装回来可以继续使用——前提是期间没有其他模组改写同一字段。

为什么不做"全局出生点"指令

有人会问能不能加一个 /setspawn 之类的通用指令。没有加的原因是原版已经有 /spawnpoint，再包一层只会让两套逻辑打架。这个模组只解决"记录维度"这一件事，其余交互保持原版。

如果你需要"跨维度传送回出生点"，那属于传送类需求，交给传送模组更合适。

和"床被破坏"的关系

床被破坏后，原版会让出生点失效（回到世界出生点）。这个模组沿用同样的规则：某个维度的床没了，该维度的记录就失效。所以它不能解决"床被熊孩子拆了"的问题，只是让不同维度互不覆盖。

如果需要"床没了也能回"，那是另一个模组该做的事。
