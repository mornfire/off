Enchantment Remover

NeoForge 1.21.1 · 1.0.0

删掉不想要的附魔。附魔台里刷不出来，战利品和交易里也不会出现，装备上已经有的直接失效。

删掉不想要的附魔。

为什么做它

附魔是原版里最容易"失控"的系统之一。一个整合包装了几十个模组之后，附魔表会被各种兼容条目撑爆，某些过于强势的附魔（或者和模组机制冲突的附魔）会变成事实上的必选。

通常的做法是改战利品表、改附魔台权重，但那些改动分散在很多地方，维护起来很麻烦。Enchantment Remover 提供的是一个集中开关：把不想要的附魔 ID 写进配置，它就从所有来源里消失。

它是怎么运作的

在 config/enchantremover-common.toml 里列出要禁用的附魔 ID（带命名空间），例如：

disabledEnchantments = ["minecraft:mending", "somemod:overpowered"]

然后三件事同时生效：

  • 附魔台：被删的附魔不会出现在可选列表里
  • 生成途径：宝箱战利品、钓鱼宝藏、村民交易、怪物掉落里的附魔书与附魔装备都不会带上它
  • 已有物品：玩家身上已经带了这个附魔的装备，名称仍然显示，但效果完全失效

第三点是刻意的：不移除附魔本身（那会导致物品 NBT 变化、可能触发其他模组的异常），只是让它在结算时不产生任何作用。

怎么用

装服务端即可，客户端不装也能生效（客户端装了只是提示更直观）。改配置后 /reload 或重启。

注意事项：

  • 附魔 ID 写错不会报错，只是不生效，建议对着 /data 或模组文档核对
  • 某些模组的"伪附魔"（自定义组件实现的）不受这个模组管辖
  • 如果服务器允许玩家自带附魔书，注意已存在的附魔书仍然存在，只是附上去之后无效

取舍与边界

不做替换。没有"把 A 附魔替换成 B"的功能，只有删除。替换会让平衡表变得难以推理。

不做等级限制。不能只删"5 级锋利"而保留"1 级锋利"——要删就整条删掉。这是为了避免出现"看似删了实际还能用"的漏洞。

保留名称显示。已有装备上的附魔名字还在，只是没效果。这在视觉上有点怪，但比静默改 NBT 安全。

版本与依赖

当前 1.0.0。NeoForge 1.21.1 / Java 21，无前置，MIT 协议。配置为 TOML，支持 /reload；卸载后已失效的附魔不会自动恢复，需要重新附魔。

与附魔类模组的配合

附魔扩展模组通常有三种实现方式：注册新附魔、改附魔台逻辑、用数据组件做"伪附魔"。Enchantment Remover 只处理第一种——真正注册进 Enchantment 注册表的附魔。后两种不受影响：

  • 改附魔台权重的模组：被禁附魔不再出现在候选里，但权重逻辑本身还在
  • 数据组件实现的"伪附魔"：不走注册表，禁用列表管不到，需要看该模组自己的配置

如果服务器同时装了村民交易扩展，注意交易里生成的附魔书也会被过滤；但已经生成的交易项不会立刻刷新，需要等村民刷新交易或重新加载。

配置维护

disabledEnchantments 是一个数组，写的是完整 ID。常见错误是漏了命名空间（比如只写 mending），这样匹配不到任何东西，也不会报错。建议维护时保留注释，写清楚每条为什么禁，方便下一个管理员接手。

改完配置后建议先 /reload，再开一个测试存档附魔一次验证。部分版本的 /reload 对附魔表的缓存不一定彻底，最保险的还是重启服务器。

版本升级时注意什么

升级游戏或模组版本后，附魔 ID 有可能变化（尤其是社区模组改名）。升级前建议导出当前的禁用列表，升级后逐条核对是否还能匹配上。

如果某条 ID 在日志里被报告"未找到"，说明它已经不存在了，留着也无害，但会让配置看起来混乱，建议清理掉。
